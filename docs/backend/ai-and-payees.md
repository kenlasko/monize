# Backend: AI assistant, payee lookup and search

The two completion paths, the continuation nudge, bulk-tool refusals, the cached brand favicon, payee contact enrichment and case-insensitive search. Read this before touching `src/ai/`, `src/payees/lookup/` or a tool description.

Paths beginning with `src/`, `test/` or `scripts/`, and layer configuration filenames, are relative to `backend/`; other source paths are relative to `backend/src/`. Explicit repository prefixes are preserved. `backend/CLAUDE.md` is the short index; this document is where the reasoning lives.

## A provider's base URL is a request the server makes on the user's behalf

Any signed-up user can add an AI provider, and its base URL is a host this server then POSTs to and reads the answer from. So where that URL may point is decided per owner, not per provider type (`src/ai/ai-base-url-policy.ts`):

- **Cloud providers** (OpenAI, Anthropic, Ollama Cloud) reach public hosts only, whoever owns them.
- **Self-hosted providers** (Ollama, OpenAI-compatible) reach a private, loopback or link-local address only when the owner is an admin (`users.role`, read from the row so a background completion gets the same answer as a request), or when the host and port are on the operator's `AI_PRIVATE_BASE_URL_ALLOWLIST` (`src/ai/validators/private-base-url-allowlist.ts`). An Ollama provider with no base URL is loopback and is checked as such.
- **The operator's `AI_DEFAULT_*` provider** is unrestricted, as before.

The policy is enforced three times, because each one alone has a gap. `AiService.validateBaseUrl` refuses the URL on create, update and draft test. `AiService.buildProvider` refuses a stored row at use time (a row saved before the rule, or by an admin since demoted) with `AiBaseUrlRefusedError`, which the provider loops surface instead of the generic "all providers failed". And every provider sends through `providerFetch(policy)` (`src/ai/providers/long-running-fetch.ts`): a request that may not reach a private address goes through the agent whose `publicOnlyLookup` (`src/ai/providers/provider-egress.ts`) refuses the connection if any DNS answer is private, so the address checked is the address connected to and DNS rebinding has no window. IP literals, which skip the lookup, are checked before dispatch. `AiProviderFactory.createProvider` defaults to `public-only`, so a caller that has not decided cannot reach a private host.

Provider requests never follow a redirect (`redirect: "error"`), and a model check that fails for an unrecognised cause returns `unverifiedModelReason` (`src/ai/providers/model-verification.util.ts`): a translated message with at most the HTTP status, never the upstream body or the SDK's error text, which is logged instead. A base URL of the user's choosing makes whatever that host answered someone else's data.

## `complete()` is not `completeWithTools()` with the tools left off

Both take `AiCompletionRequest`, but `complete()` maps messages through `toSimpleMessages`, which **filters `role: "tool"` out entirely** -- summarising a tool-use conversation through it sends a transcript stripped of every tool result and returns a confident summary of nothing.

A tool-free turn over a tool-use transcript goes through `completeWithTools`/`streamWithTools` with an empty tool list, and every provider builds the field with `toolsField` (`src/ai/providers/tools-field.util.ts`) so it is **omitted** rather than sent as `[]` (OpenAI rejects `tools: []`). `tools-field.util.spec.ts` scans every `*.provider.ts` for a bare `tools:` key; per-provider specs assert the request body both ways. The one caller is `AiQueryService.streamFinalSynthesis`, the pass that turns an unfinished investigation into an answer.

## A turn that ends on a promise is not an answer

Nothing runs between turns, so a tool-free turn saying "One moment, I'm gathering..." ends the query (the loop exits on `stopReason !== "tool_use"`) and reads as a hang. The loop therefore does not treat every tool-free turn as an answer: `isDeferredContinuation` (`src/ai/query/continuation.ts`) recognises the promise, and the loop replies with `CONTINUATION_NUDGE` in the user's place for at most `MAX_CONTINUATION_NUDGES` passes, then breaks to the tool-free synthesis pass with `cutoff = "stalled"`. The stalled text stays in the thinking buffer and never becomes the answer bubble.

Detector shape (both asymmetries are in its spec): a wait request ("one moment") is decisive; a bare work announcement is not, and an offer ("let me know", a trailing `?`) wins over it; only the tail of the message is examined. A false positive costs one extra pass; a false negative is the hang. The strongest signal needs no prose judgement: `promisesPendingAction` pairs a promise of confirmation cards against `proposingToolResults === 0` -- prefer pairing a text claim against state the loop already tracks over adding another regex phrase. `QUERY_SYSTEM_PROMPT` asks for the same thing, but a prompt rule is not a guarantee.

**A stall is often a dead end the model found and could not name.** Both reported stalls were a request the tools could not express (recategorizing one line in 17 split transactions, with one proposing call allowed per query). Batch rows now carry `splits` (`BatchUpdateTransactionRow.splits`, applied in `executeBatchRow` inside the same `UpdateTransactionDto` as the scalar fields, per invariant I1); the individual-card path passes `result.splits` through. Two rules the tests hold: a row that resends no splits must carry none (an empty set would rewrite the lines it was asked to leave), and a row's preview shows its lines instead of a category name. The general point: when you add a limit, put it in the tool description in the same commit.

**A filtered read is not a complete read, and only one of its two readers can tell.** `applyCategoryFilters` hydrates only the split lines matching the filter -- right for the register, wrong for anything that sends the lines back, because `manage_transactions` replaces a split set with exactly what it is given. The LLM path reloads the full set per split parent (`loadCompleteSplits`). Before reusing a list query in a tool, ask what its `where` does to the collections it hydrates: a filter on a joined child table silently truncates the parent's children.

**A refusal the caller cannot act on is a refusal that ends the task.** Every bulk tool path computes a per-row reason; `describeSkippedRows` (`common/bulk-create.types.ts`) is the only way those messages are built (identical reasons collapse with a count; distinct ones list up to three). `bulk-skip-reporting.spec.ts` scans all four tool sources and fails on a "None of ... could be prepared" message that does not carry its reasons -- a generic message that *guesses* sends the reader away from the fix. Individual-card paths that count skips collect reasons too.

## A cached brand favicon is four columns, one fetcher, and one export rule

Institutions and payees resolve a website's favicon server-side and cache the bytes so the browser never contacts a third party. Shared code lives in `src/common/favicon/`: `FaviconService` (the gstatic fetch, with timeout, size cap and image-only content-type check) and `brandLogoColumns` (the four columns `logo_data`, `logo_content_type`, `has_logo`, `logo_fetched_at`). A third entity imports `FaviconModule`, not a copy. Four shared rules, each with a test:

- **The fetch stays outside the transaction** -- best-effort, never fails the create/update, never holds a connection on a slow host.
- **Re-resolve only when the address actually changed.** The form resends the current website on every save, and a failed re-fetch would clear a good icon. Clearing the address clears the icon.
- **The flag and the bytes move together.** `has_logo` answers every list read (the bytes are `select: false`, leaving only through `GET /:id/logo`, which 404s so the client draws its own badge); `logo_fetched_at` stamps the *attempt*.
- **A bytea column breaks `SELECT *`.** The export query must list columns and wrap the bytes in `encode(logo_data, 'base64')` (`export-driver-values.spec.ts` catches the omission). The support backup drops the bytes and forces `has_logo` false, because a brand icon re-identifies a masked payee.

## Contact enrichment: the background path fills gaps, the user confirms the rest

A payee's website, address, email and phone can be looked up from one of two sources (`src/payees/lookup/`, opt-in via `user_preferences.payee_contact_lookup_enabled`): **Google Places** where it is configured, and the user's **AI provider** otherwise. Every adapter -- Anthropic and OpenAI with their server-side web search, Ollama from model knowledge, the MCP relay through the user's own agent -- answers through `AiService.completeWithWebSearch`, which reports whether a search actually ran; `sanitizeContactSuggestion` applies the DTO's shape rules to every answer and, for an unverified source (`ai-knowledge`, `ai-relay`), keeps address and phone only at high confidence. `PayeeContactLookupService.lookup` is the one door and never throws: `disabled`, `no_provider`, `failed` (with the relay's own message as `detail`) and `none` are four outcomes a caller has to tell the user apart, and a failure is never shown as "nothing found" -- `none` means the source answered and had nothing (a parsed `{"matches": []}`), while an unreadable answer (an empty turn, an output truncated at the token cap, prose from a relay agent) is `failed`, because `none` is the reason that stamps `contact_lookup_at` and retires the automatic lookup for that payee.

Seven rules, each with a test in `payee-contact-enrichment.service.spec.ts`, `contact-suggestion.sanitize.spec.ts`, `payees.controller.spec.ts` and `payees.service.spec.ts`:

- **A lookup never overwrites a value the user entered** (INV-PAYEE-001). The only write a *lookup* makes is `ENRICHMENT_UPDATE_SQL`, on the background path after a name-only create: every contact column is `COALESCE(column, $n)`, `contact_lookup_source` moves only when this statement set a field, and `contact_lookup_at IS NULL` makes it run at most once per payee, on any replica.
- **The detail screen's button proposes; the user's confirmation writes.** `POST /payees/:id/lookup-contact` (`PayeesService.lookupContactForPayee`) reads the row for its ownership check and its context, returns the candidates and touches nothing. `ContactLookupDialog` shows each field as an add or a replace beside the value it would replace, and the confirmation goes through `PATCH /payees/:id` -- an ordinary payee edit, which is what makes replacing a stored value legitimate there when the lookup itself may not. There is deliberately no COALESCE re-run any more; `PayeeContactEnrichmentService` serves the background path alone.
- **What the user already holds is context, and a fuller answer for it is an offer.** Every lookup carries `PayeeLookupContext` (`lookup/lookup-context.ts`: website, address, email, phone and notes, sanitized and capped) so the model answers for the right organisation and the right branch of it -- an address reading "Toronto" is a *constraint*, not an answer to preserve. `sanitizeContactSuggestion` therefore classifies each field three ways against that context: a fill (nothing was there), a **refinement** (something was, and this is fuller -- named in `PayeeContactSuggestion.refined`), or an echo (the same fact, dropped so it cannot be reported as found). Notes are context only; no lookup writes them.
- **A name can mean more than one business, so the answer is a list.** `sanitizeContactSuggestions` reads `{ matches: [...] }` (a bare object is still one match), caps it at `MAX_CONTACT_LOOKUP_MATCHES`, and **drops an alternate the user could not tell apart** -- no `label`, or a label already used -- because a picker whose rows read alike is worse than no picker. `ContactLookupOutcome`'s `ok` arm is a non-empty tuple, so a surface with nobody to ask (background enrichment, the AI/MCP create preview) reads `suggestions[0]` and only a surface with a user offers the rest.
- **A client that will ask the user takes the lookup off the server.** `POST /payees` accepts `deferContactLookup`, which the controller reads as an *option* and never lets reach the row: it says the caller runs the lookup itself and shows the answer for confirmation (the transaction page's payee quick-create does, through `usePayeeContactLookup` and `ContactLookupDialog`). Without it the same payee is looked up twice -- two paid calls -- and the background write stores values while the user is still reading the dialogue offering them.
- **A lookup never fails a create, and it runs after the commit.** `PayeesService.create` dispatches the background enrichment only when the row carries no contact detail, the preview did not already look up, and `getActiveScopedManager()` is undefined -- "the callback resolved" only means "committed" when nobody upstream opened a transaction we joined, and a dispatch inside one would look for a row nobody else can see. The dispatch runs under `withUserContext` on the request's tail and logs its failure.
- **The preview looks up so the card and the commit agree.** A single AI/MCP `create_payee` preview with no contact details runs the lookup (`previewCreate(..., { lookupContact: true })`) and hands its stamp down the descriptor to `create(..., { contactLookup })`, which stores that provenance instead of looking up again. Batch rows are enriched after they commit instead -- 25 model calls inside one chat turn is the wrong latency budget -- and both tool descriptions say so.

- **The user picks the ORDER, and the second source answers for exactly one class of reason.** `RoutingPayeeContactLookupProvider` is the only implementation bound to `PAYEE_CONTACT_LOOKUP_PROVIDER`; it asks `PayeeLookupSettingsService.resolveRouting` for whose key pays AND which source goes first, in one read (the operator's `GOOGLE_PLACES_API_KEY` wins over a user's own -- the env-var rule, and the deployment has already paid for it), claims a slot against that key's monthly cap (INV-PAYEE-002), and calls Places. `preferredSource` defaults to `google-places`; `ai` is offered because Google holds no email address. `ai_provider_config_id` (migration 190) pins WHICH provider answers: the assistant falls through every active provider in priority order, which is right for a chat turn and wrong for a lookup billed per call, so a pin that resolves to nothing -- the provider was deactivated, which the `ON DELETE SET NULL` foreign key cannot see -- reports `no_provider` rather than spending a model the user did not choose. `AiService.getActiveConfigs(userId, onlyConfigId)` narrows the list, and returns EMPTY for an unmatched pin (never the full list, and never the centrally managed provider, which is the deployment's and carries no pin). The id is verified against the caller's own configs inside the transaction that stores it. The other source is reached **only when the first cannot answer for a configuration or budget reason** -- no AI provider configured, or the cap spent -- because the cap is a budget the user chose and stopping outright would turn their own limit into a broken feature. A Places *failure* -- rejected key, API not enabled, open breaker -- is reported as `failed` carrying Google's own message, never absorbed into an AI bill the user never sees; and when the cap is spent with no AI provider behind it, the reason is `quota_exceeded`, not `no_provider`, because the two name different repairs. The field mask asks for `internationalPhoneNumber` and never `nationalPhoneNumber`: a suggested number is normalized with no region, so one without a country code is dropped on arrival every time.

  **A secret is only as private as the error messages it can appear in.** The Google Places key is encrypted at rest and never returned to the client -- and `fetch` refuses a header value holding a control character while QUOTING that value in the `TypeError` it throws, so a key carrying one travelled verbatim into the application log (via `ProviderHealthService.logFailure`) and into the Test button's error text. Both doors now ask `isSendableApiKey` (`src/payees/lookup/google-places/google-places-key.ts`): the DTOs refuse to store such a key, and `GooglePlacesClient` refuses to send one stored before that validator existed or supplied through `GOOGLE_PLACES_API_KEY`, which no DTO ever sees. The refusal is raised BEFORE the breaker is consulted -- nothing was asked of Google, so it is neither an outcome nor a probe worth holding -- and names the problem, never the key. The general rule: before putting a user-supplied value in a header, a URL or an exception message, ask what the platform does with a value it rejects.

  **Each source carries its own switch, and off means NOT REACHED.** `google_places_enabled` (migration 188) and `ai_enabled` (migration 191) are symmetric: a source switched off is not asked first, and is not the fallback when the other cannot answer. Anything less would defeat the one thing a switch is for -- that the source stops costing the user money -- and it is why the router models the AI switch as a distinct `DISABLED` sentinel rather than reusing `ai_provider_config_id`'s `null`, which already means "no pin, ask every active provider" and is the exact opposite. With Places off and AI off, `getStatus` answers `available: false` (a *configured* AI provider is not a *usable* one), so the settings screen renders the automatic-lookup toggle off and disabled rather than offering a lookup nothing can answer; the router reports `no_provider` when nothing is reachable at all and `quota_exceeded` when Places was reachable and its cap is spent, because those are two different repairs.

  **The user's own counter travels with a backup; the deployment's does not.** `payee_lookup_usage` is exported and restored so a month's spend survives a move to another machine -- the Google key is the same key and the free allowance is counted against it, not against the server. It is the one entry in `PRESERVED_ON_RESTORE` (`src/backup/restore-plan.ts`): the restore does NOT clear it first, so the insert's `ON CONFLICT DO NOTHING` gives the archive's count to a machine that has no row and leaves a live count alone. A restore therefore cannot lower one and hand back quota Google has already billed for, and the only way an archive's count can legitimately be the higher of the two is that the live one was lost -- which is precisely the case with no row to conflict with. `google_places_instance_usage` stays out of the export entirely: it has no `user_id`, it counts a key that comes from deployment configuration a backup does not carry either, and every user on the instance spends it, so a per-user archive writing it would overwrite a counter other users are still spending.

  The cap is counted in **Pacific** calendar months (`GOOGLE_PLACES_QUOTA_TIMEZONE`), not UTC, because that is when Google's free allowance resets -- a counter that rolled over first would hand back a cap the allowance behind it had not released, and every request in that window is billed. The reset needs no job: `month` is half of `payee_lookup_usage`'s primary key, so a new month simply addresses a row that does not exist yet. And a request Google **answered with a refusal** was never served and never billed, so the Test button hands its slot back (`PayeeLookupQuotaService.release`); a transport failure does not, because nobody answered and under-counting is the direction that costs money. A server sends no `Referer` of its own, so an HTTP-referrer restriction rejected every lookup with "Requests from referer <empty> are blocked"; the client now sends `PUBLIC_APP_URL`'s origin as `Referer` (Node permits the header browsers forbid), which makes such a key work. **It buys availability, not security**: a referrer restriction protects a key that is public -- shipped in browser JS, where the browser sets the header -- and this key never leaves the server, so anything holding it can send that header too. Only an IP restriction constrains a server-side key; the header is sent because a deployment with no stable egress address cannot use one. `testKey` names the exact referrer it sent, since a restriction written `*.example.com/*` does not match a bare `example.com`, and says so differently when `PUBLIC_APP_URL` is unset -- two different repairs behind one Google message.

## A payee merge moves every reference before it deletes

Both merges, the Merge dialog (`PayeesService.mergePayees`) and Auto-Merge (`PayeeAutoMergeService.applyAutoMerge`), move the source payee's rows with `reassignPayeeReferences` (`src/payees/payee-references.ts`) before they delete it, never with an `update` of their own (INV-PAYEE-003). Transactions and scheduled transactions have no `ON DELETE` action and the aliases cascade, but every other foreign key to `payees(id)` is `ON DELETE SET NULL`, so a column left out is cleared by the delete without an error. Both routes are owner-only; a delegate path would need the two `shared_*` statements revisited, because those policies require the real user to be the owner and the UPDATE would match nothing. A new reference to payees gets its entry in `PAYEE_REFERENCE_MOVES` in the same migration's PR; `payee-references.spec.ts` names the column when it is missing.

## A case-sensitive `LIKE` is not a search

Postgres evaluates `LIKE` case-sensitively, so `Like('%amazon%')` matched nothing while `Like('%Amazon%')` matched -- and the tool built on it looked as though it only accepted exact names (its own description had promised a "case-insensitive substring match" for as long as it had been wrong). Where a filter is offered to a person or a model, match case-insensitively: `ILike`, or a comparison the code performs itself. `PayeesService.getLlmPayees` is the worked example, and its spec asserts that a lowercase query and an uppercase one return the same rows.

**And a filtered list says how much it left out.** `getLlmPayees` returns `totalCount` (what matched) beside `payees` (what came back) and a `truncated` flag, because a capped list presented as the whole one is the same defect as a subtotal presented as a total.
**A match key is not a display value.** Matching case-insensitively means a `LOWER(TRIM(...))` column or a lowercased map key, and that key never reaches a response: the Bill Payment History report put `payee_name_normalized` on screen, so every payee read in lowercase. Select or carry the name as the user wrote it beside the key, and return that. `tax-recurring-reports.service.spec.ts` holds the case with a mixed-case scheduled payee.

## Transaction search syntax

The Transactions search string is a small query language: bare words are AND-ed, `"quotes"` make a phrase, `-` excludes, `field:text` is contains, `field:=text` is exact and `*` is a wildcard, over the fields `payee`, `memo`, `cat`, `tag`, `account`, `ref`, `amount`, `date`, `status`, `is` and `has`; `#10` is `ref:=10`, and amounts and dates take `>`, `>=`, `<`, `<=` and `a..b`. The design, the grammar and the truth tables are `docs/specs/advanced-search.md`.

- **One door.** A search string reaches SQL only through `applyTransactionSearch` (`src/transactions/apply-transaction-search.ts`), or its two halves where one parse feeds several queries (the register's page, target-page lookup and balance windows). The string is passed raw and escaped once, inside the builder; `transaction-search.guard.spec.ts` fails a hand-built `%...%` pattern in the transactions module (INV-SEARCH-001, INV-SEARCH-005).
- **Split grain everywhere.** Every call site searches the split line it already joins, so every term must hold on the same line, the register draws only matching lines with a filtered total, and bulk update selects the transactions the register lists (INV-SEARCH-003). Which lines of a selected split a bulk category change rewrites is still the category filter's decision, not the search's.
- **One description per reader.** `SEARCH_SYNTAX_SUMMARY` is the `searchText` description in both `list_transactions` adapters; it rides in the MCP `tools/list` budget and the 300-character field cap, so it is terse and its field list is ordered so it never reads as the `sortBy` enum. The Swagger text of every `search` parameter is one fuller paragraph in the controller.
- **The register echoes what it read.** `GET /transactions` returns `searchInterpretation` (each term's field, operator, value, negation, the raw text and an `ignored` reason) whenever a search was sent, so the client shows how a string was read without a parser of its own. The delegate path that returns an empty page for a delegate with no visible accounts carries no echo.

## Shared AI tools (AI Assistant + MCP server)
Every AI tool that reads or aggregates data shares one implementation between the AI Assistant (`backend/src/ai/query/tool-executor.service.ts`) and the MCP server (`backend/src/mcp/tools/*.tool.ts`). Put the shared logic on the relevant domain service (e.g. `PortfolioService.getLlmSummary`, `TransactionAnalyticsService.getTransfersByAccount`); the two tool layers are thin adapters returning the same data shape (the AI executor wraps `{ summary, sources }`; MCP just `toolResult(data)`s it). Adding a tool means wiring both layers in the same PR -- never ship to only one.

**A tool's parameter reaches the domain service under its own meaning.** Both adapters call the domain method with each value in the position it is named for, and a default the tool leaves open is the domain service's own constant, so the assistant, MCP and the Reports page answer one question alike: `generate_report` `spending_anomalies` passes `SPENDING_ANOMALY_DEFAULT_THRESHOLD` and the requested `months` window (default `SPENDING_ANOMALY_DEFAULT_MONTHS`, six) to `AnomalyReportsService.getSpendingAnomalies` (`src/built-in-reports/anomaly-reports.service.ts`), where the months were once passed as the z-score threshold (audit A26-M34). Each adapter spec asserts the full argument list, never only the user id.

**A model never converts a currency.** Anything a model reads about an account carries its figure in the reader's default currency beside its own (`getLlmAccounts`: `balanceInDefaultCurrency`, `currentBalanceInDefaultCurrency`, `exchangeRate`, with `defaultCurrency` and `missingRatePairs` at the top), and any other conversion goes through the `calculate` tool's `convert` operation, which prices it with `ExchangeRateService.convertOnDate` at the rate for a date (today by default) and reports the rate and its date. A pair with no rate is `null` on the account and an error from the tool -- never a guess, never `1`.

**A model never adds currencies either.** `list_transactions`, `compare_periods` and the MCP `financial-summary` and `recent-transactions` resources take their totals from `TransactionAnalyticsService` (`getLlmListTransactions`, `getLlmPeriodComparison`, `getLlmFlowTotals`), which converts each row into the reader's default currency at the rate for its own date (`buildRateIndex` and `convertAtDate`, inside the read's own `withScopedDb`) and accumulates through `FxAggregate`. Each answers `totalsCurrency`, `fxComplete` and `missingRatePairs`; while a pair has no rate a total is `null` and the converted part rides as a `known*` subtotal, and the executor's summary line names the currency, or says the totals are withheld and names the pair and the Currencies page. The per-currency `byCurrency` view stays unconverted and labelled.

`fetch_bond_series` (`countryCode`, `seriesCode`) is the shared tool over `BondSeriesService.fetchSeries` (`src/bonds/bond-series.service.ts`): it takes no rate, fee or date, writes only reference data read from the issuer's official source (INV-BOND-006), so it carries no confirmation card; the executor and `src/mcp/tools/bond-series.tool.ts` both return the instrument with `created`, or the refusal's translated `errors.bonds.<code>` message. `fetchSeries(userId, ...)` charges every attempt, failures included, to one per-user allowance of 10 a minute on the shared `auth_attempt_counters` row before any request goes out (429 `SERIES_FETCH_RATE_LIMITED` on REST, the executor and MCP alike), and the tool is withdrawn from any assistant run whose prompt carries untrusted content (`NETWORK_WRITING_TOOL_NAMES`, used by the email parser generator). The MCP-only `enter_bond_series_manually` is the administrator's fallback (role checked with `BondSeriesService.isAdministrator`, values validated by `checkManual` before the `confirmWrite`); the assistant has no form of it.

`list_warranties` (`status`, `q`, `limit` up to 50) is the read-only shared tool over `WarrantiesService.getLlmWarranties` (`src/warranties/warranties.service.ts`), which reads through the list route's `findAll`, so every row's `status` and `daysLeft` are the server's (WTY-002); neither adapter passes an account scope, because an MCP credential is the owner's own and a delegate reaches the assistant only with READ on every account (`DelegateRequiresFullScope`), and `linkedTransactionId` is null whenever a scope would hide the purchase (WTY-007).

An acting delegate's assistant run offers `FINANCIAL_TOOLS` filtered to `DELEGATE_ALLOWED_AI_TOOLS` (`src/ai/query/ai-query.service.ts`), an allow-list: a new tool is withheld from delegates until it is added there on purpose, and a call to any other name is refused at execution, not only left out of the offered list. A tool is allowed only when it reads what a full-scope read-only delegate can already read through REST; a `manage_*` tool, a write, and anything behind an owner-only or non-`@AllowDelegate` route is not. `delegate-ai-tools.guard.spec.ts` fails when a tool is in neither `DELEGATE_ALLOWED_AI_TOOLS` nor `DELEGATE_DENIED_AI_TOOLS`, or in both; the denied list is read by that test only. The MCP server is out of scope (its credential is the owner's own).

`manage_investment_transactions` takes an optional `bondSeriesCode` (a code such as `EDO1036`) on a row of a security linked to a bond program, in both layers: `InvestmentTransactionsService.previewCreateInvestmentTransaction` resolves it within the program through `resolveTransactionSeries` (the same function the write calls, so a card never shows what the commit would refuse), shows the resolved series' code on the card, and carries the resolved id as `bondInstrumentId` in the signed descriptor; every commit path (AI executor, MCP) forwards it to `create`/`update`, where it is checked again (INV-BOND-007). A purchase with no code takes the series on sale on its date; a sale with none leaves the oldest lots first across series. For a REDEEM of such a security the same preview asks `BondHoldingsService.redemptionSplit` and fills what the caller left out (price = principal returned per bond, `accruedInterest` = the interest; also from a price equal to the whole payout), refuses the card when the split is refused, keeps figures the caller gave for both and marks the card `differs`; the series and the split ride on the card (`bondSeriesCode`, `bondRedemptionSplit`), and `accruedInterest` rides in every create/update descriptor so a commit writes the INTEREST companion the card showed (INV-BOND-009; `src/securities/bond-redemption-fill.util.ts`).

## Rule tools: names in, ids out, and a test that writes nothing

`list_transaction_rules` and `manage_transaction_rules` (`operation`: create, update, delete, run, test) share one door, `TransactionRuleToolPrepService` (`src/transaction-rules/rule-tool-prep.service.ts`), the way `manage_payees` shares `PayeeToolPrepService`; the assistant's executor is a thin adapter over it, and the MCP tool must be another. The model writes and reads the **name form** (`rule-name-mapping.ts`): a leaf on `accountId`, `payeeId`, `categoryId` or `tagIds` carries names, an action carries `categoryName`, `payeeName` or `tagNames`, and `list_transaction_rules` returns that same form, so a rule read can be sent back. `settle_loan_installment` is one more structural action in that table: `loanAccountName` (an account) and `interestCategoryName` (a category), both directions; a model writes it exactly like `convert_to_transfer` or `split`, never with `loanAccountId`.

- **Names resolve through the resolvers the other tools use** (`AccountsService.resolveAccountFilter`, `PayeesService.resolveByName`, `resolveCategoryNamePaths`, `TagsService.findAll`); there is no second one. A name that is not exactly one row is refused with `NAME_NOT_FOUND` or `NAME_AMBIGUOUS` at its path, with the closest names, before any validation runs.
- **A refusal is a tool error carrying the REST API's `{ path, code }` entries, never a card.** Shape and ownership come from `previewDraft` / `previewRun`, which validate exactly like the write. A run or an edit that would change nothing is refused too: a card must never be an approval for nothing.
- **The descriptor carries ids; the card carries the names of those ids** (`AiActionRulePreview.labels`) and the client renders the rule in words with its own translations. An update's descriptor names the revision it was built from, a delete's the same, and a run's the plan fingerprint; confirm commits through `TransactionRulesService` / `TransactionRulesRunService`, which check ownership and the expectation inside the write's transaction, so a stale card is a 409 with nothing written.
- **`test` shares the path and proposes nothing**: it is `previewDraft` for a draft and `previewRun` for a saved rule, and it builds no descriptor. A run confirmed from a card counts as one write against the daily cap, however many rows it changed.
- **The MCP tool commits an approved card through `AiActionsService.commitApproved`**, the executors `/ai/actions/confirm` uses, so a rule is validated and revision-checked once whichever surface approved it. It skips the signature, expiry and anti-replay claim because the descriptor never left the server; the MCP write cap is the caller's (`McpWriteLimiter`), and a relay card goes first exactly as for the other `manage_*` tools. Never pass it a descriptor read from a request.

## The AI review queue: a proposal is a stored card, approval marks it applied in the write

`ai_review_requests` (`operation`: list, claim, submit, reject) is one tool on both surfaces, over one door, `AiReviewWorkService` (`src/ai-review/ai-review-work.service.ts`); the review inbox's REST routes (`GET /ai-review-requests`, `POST /ai-review-requests/:id/dismiss`) are a third adapter over it. The assistant claims under the key `assistant`, an MCP client under its `callerKey`. `claim` takes an optional `requestId` (`claimById`) for a caller that already holds the id, such as the receipts page's "Recognize with AI", which opens the chat with the request queued; without it, the oldest pending request.

`email_receipt_parsers` (`operation`: test, save_draft, categories, get) is the second tool over the receipts parser door, `EmailReceiptParserToolsService` (`src/email-receipts/parsers/email-receipt-parser-tools.service.ts`, in the leaf `EmailReceiptParsersModule` that the assistant's and the MCP server's modules import by `forwardRef`). A parser draft is a request of kind `email_parser_draft` (`POST /email-receipt-parsers/draft-with-ai` queues it for up to 25 chosen emails (five per sender domain, at most five domains, one for a trade draft; a 400 before any write otherwise); one open request per user and sender domain, a new one replaces the stale one under `LockScope.AiParserDraftRequests`). `ai_review_requests` `claim` by id returns the emails' capped text under `emailReceipts` with the parser guidance (`AI_REVIEW_PARSER_DRAFT_GUIDANCE`) and refuses `submit` for this kind; the agent runs `test` over the same emails (it reads the lines of the definition's `source`, `text` or `html`; the guide explains both) and saves with `save_draft`, which stores a DISABLED parser through the same validation as the editor and marks the request applied. Approving the draft in the parsers screen marks it applied, deleting it dismisses the request. Nothing in the tool changes the ledger or reads the mailbox (INV-RECEIPT-003 is untouched), so it carries no confirmation card and no write cap; `get` returns the user's parsers as summaries, or with `parserId` one parser in full in any status (`getParser`: the editor's view with category names and `payeeName`, a foreign or malformed id is a 404), to start a new draft from; the wizard's queued revise instruction carries the draft's `parserId` for it. `test`, `categories` and `get` need `read`, `save_draft` needs `write`. The assistant's form of the tool (not the MCP entry, whose `tools/list` bytes are budgeted by `src/mcp/tools-list-budget.spec.ts`) also takes `samples` on `test` (each email with the transaction it paid for; the result says per email whether the parsed date and total agree) and `parserId` with `expectedRevision` on `save_draft` (an in-place update of a draft under the row lock, a stale revision is a 409). The profile wizard's `POST /email-receipt-parsers/generate-with-ai` runs that loop synchronously through `AiQueryService.executeQuery` (`src/email-receipts/parsers/email-receipt-parser-generate.service.ts`, in `EmailReceiptsModule` because the leaf parsers module cannot import `AiModule`) and reads the saved draft back from the database (it decides the route first: a direct tool-capable provider runs now and returns `{ status: 'saved', parserId, revision, answer }`; a user whose top provider is the MCP relay gets an `email_parser_draft` request queued, `AiReviewRequestsService.queueParserDraft` replacing an unclaimed one and refusing a claimed one with a 409, and `{ status: 'queued', requestId }`; `GET /email-receipts/domains/uncovered` carries `pendingRequestId` for the wizard to wait on; `save_draft` with a `requestId` updates the newest unapproved draft covering the request's domain instead of adding another; a request over several domains takes one draft per domain while `claimed` or `proposed`, `proposal.parserIds` lists them, it is `applied` only when every listed parser is approved and `rejected` only when none exists any more, and `test` takes `componentDrafts` to join a settlement's parts to unsaved components without writing: `docs/specs/email-receipt-linked-receipts.md` 10a); `POST /email-receipt-parsers/:id/preview` runs the same dry run (`src/email-receipts/parsers/receipt-dry-run.ts`) read-only over the domain's emails.

A trade-confirmation email read by a profile with a `trade` section is a request of kind `email_trade` (`docs/specs/email-receipt-trades.md`): it has no transaction, is born claimed by `EMAIL_RECEIPTS_CLAIM_KEY` so no agent can claim it, and its proposal is a signed `create_investment_transaction` card stored by `AiReviewWorkService.submitTrade`. The receipts page's "Recognize as a trade" (`POST /email-receipts/:id/ask-ai` with `asTrade`) queues a PENDING `email_trade` request instead, which the assistant or an MCP agent claims by id and answers with `submit` and the `trade` field (`aiReviewAgentTradeSchema`: the account by name or id, action, symbol, quantity, totalAmount, optional commission, currency, date and description); `submit` accepts `trade` for this kind only. Both surfaces go through the same `tradeFromAgent` and `buildTradeCard`, so the refusals are the profile's. The inbox and the bulk approval rebuild that card from the stored trade (`buildTradeCard`: the strict ticker lookup `SecuritiesService.resolveByTradeSymbol`, then `previewCreateInvestmentTransaction` with the executed total and no price), and confirm marks the request applied inside `InvestmentTransactionsService.create` through its `beforeWrite` hook (`AiReviewRequestsService.markTradeApplied`).

The review inbox approves in bulk through `POST /ai-review-requests/approve-batch` (`AiReviewApprovalService` / `AiReviewApprovalController`, in `AiModule`, so the receipts module imports the AI module and never the reverse). For each id it rebuilds the card with `AiReviewWorkService.buildApprovalCard` against the transaction as it is now and calls `AiActionsService.confirm`, one transaction per request, so the signature, the single-use claim, the revision check and the daily write limit all apply as for a single approval; a refusal leaves that request proposed and is listed in the answer. A profile-built proposal (claimed by `EMAIL_RECEIPTS_CLAIM_KEY`) is exempt from `AiWriteLimiter` when the user's mailbox switch `profile_proposals_count_toward_ai_limit` is off: `confirm` reads the stored request and the stored switch (`AiReviewRequestsService.isExemptFromWriteLimit`) and a request body can never claim it. A profile's `tag` reaches the transaction as `tagNames` on the card (`AiReviewProposalInput.tagNames`, find-or-create by name, additive), and a profile's `aiCategories` asks the AI for item categories through `EmailReceiptCategoryAiService` (`AiService.complete`, feature `email_receipt_categories`) only when `AiService.canAnswerNow`, never inside a database transaction (`docs/future-plans/email-receipts.md` 5.6, 7.1, 8.1).

- **A proposal carries no amount, date or account.** It is the reviewed transaction's category lines, or one category, payee or description, expressed as `manage_transactions` takes an update (`aiReviewRequestsFields` in `tool-input-schemas.ts`). It is prepared with `TransactionToolPrepService.prepareUpdate` and built by `buildUpdateTransaction`, so the checks are the chat's. Lines that do not add up to the amount are refused **naming the difference** before anything is stored; a transfer is refused (reject the request instead). Tags are not part of the update tool's input and so not of a proposal.
- **The stored proposal is the input plus the signed card, for the record; what the person approves is rebuilt.** A card is signed for ten minutes and describes the row as it was, so the inbox rebuilds it from the stored input against the transaction as it is now (`listInbox`). A later edit that breaks the proposal shows its reason in place of a card; it never overwrites the edit.
- **Approval marks the request applied in the write's own transaction.** The card's descriptor carries `aiReviewRequestId` (signed, not an envelope field), and `AiActionsService` passes `TransactionsService.update` a `beforeWrite` hook that runs `AiReviewRequestsService.markApplied` on the write's manager, after the row lock and before any write. A request that was dismissed or expired since the card was built matches nothing and refuses the edit with a 409 and nothing written; a failure after the mark rolls it back.
- **Nothing here re-claims a stale claim.** A claim whose agent went away stays `claimed` until the request expires or the person dismisses it.

## A filter narrows the list it was applied to, never a total about the window

`kind: "deposit"` on the AI/MCP rollup left `bills` empty and published `totalUpcomingBills: 0` with `amountsComplete: true` over a window holding a 1,200 bill -- a confident "nothing is due" in place of an answer nobody asked for. The buckets and the unknown-amount names all come from the rollup base (every filter except `kind`); only `items` and the counts follow the caller's filter, and both tool descriptions say so. The previous pass fixed exactly this for the `unknown` bucket and left the other two on the filtered list, which is the shape to look for: when a fix moves one member of a set off a wrong source, move all of them.

## The insights aggregator reads the user's own calendar

`InsightsAggregatorService.computeAggregates` (`src/ai/insights/insights-aggregator.service.ts`) takes "today" from the user's effective timezone (`getEffectiveTimezoneOfUser`, `todayInTimezone`) and derives the month windows from that `YYYY-MM-DD` string. Never from a local-midnight `Date` read back with `toISOString()`, which put a Warsaw user in the previous month (A26-L29).
