# Backend: transactions, exports and money

Exporter labels, blank transfer payees, scheduled loan interest, category identity, the currency a value carries, fallbacks and the Money import mapping. The cross-layer money rules are in `AGENTS.md` and `docs/financial-semantics.md`; this document holds the backend decisions that implement them. Read this before touching a transaction write, an export or a loan or category derivation.

Paths beginning with `src/`, `test/` or `scripts/`, and layer configuration filenames, are relative to `backend/`; other source paths are relative to `backend/src/`. Explicit repository prefixes are preserved. `backend/CLAUDE.md` is the short index; this document is where the reasoning lives.

## A deletion removes every row it would orphan, on every path that deletes

A split-transfer leg's `linked_transaction_id` names its split PARENT, not a mirror leg; only a plain transfer's link names the other leg. A path that treats the link as "the other leg" deletes the parent, lets `transaction_splits` cascade and leaves every sibling leg standing with its money and a NULL link, which agrees with its own account's ledger, so no recompute ever repairs it (A26-H05). So every delete path expands a split-transfer leg to the parent's whole set, as `removeTransferFromSplitInTransaction` does: `TransactionBulkUpdateService.bulkDelete` finds the parents of the selected legs, locks the parents on their own first (the by-role order of `common/db/locks.ts`), reads their split rows under that lock, then locks every leg ascending and reverses each locked row through `deletionBalanceEffect`. A cross-owner counterpart is outside the caller's owner-scoped lock and is detached by the `ON DELETE SET NULL`, the frozen semantics of the single delete. `test/integration/bulk-delete-split-leg.integration.spec.ts` runs on the schema's own foreign-key actions and asserts them first. INV-BALANCE-001.

## A closed account holds zero including what is already booked

`AccountsService.close` checks, under the account's row lock and over both halves of an investment pair, that `current_balance` is zero, that a brokerage holds no securities, and that no non-VOID top-level row is dated after today. A future-dated row is not in `current_balance` yet, so "zero now" let an empty account with a -25.00 row dated next week close, and on that date the due-balance pass moved the closed account to -25.00 (A26-M12). The refusal names the count and the repair (delete or void the rows). The due-balance pass keeps applying a row that falls due on an account closed before this check existed: skipping it would leave the stored balance off its ledger, which is the worse of the two states. `test/integration/account-close-pending.integration.spec.ts`.

## A label the exporter writes itself must need no escaping

The CSV formula-injection guard in `account-export.service.ts` exists for user-controlled text; when one of the exporter's _own_ strings trips it (`-- Split --` got an apostrophe prefix on every split parent row), rename the label so it opens with a character no spreadsheet evaluates (`CSV_SPLIT_CATEGORY_LABEL` is `(Split)`) -- do not exempt the literal. Assert the _field_, not the line (`toContain` is satisfied by the neutralized cell), and keep the document-level check: export an all-ordinary-text fixture and assert no cell carries the guard's prefix.

A transfer's label is `csvTransferLabel` in the same file, and it names the direction as well as the counterpart (`Transfer To Savings`); a split line is asked with its own amount, not the parent's. Its twin is `transferCsvLabel` in `frontend/src/lib/transfer-label.ts`; the QIF export keeps Quicken's `L[Account]` form deliberately.

## A blank transfer payee is stored blank and resolved at read time

A transfer created without a payee persists `payee_name` as NULL (issue #1214); the display label is resolved per read from the linked leg's account -- its CURRENT name, in the reader's language. The English form for machine-facing surfaces (CSV/QIF export, AI/MCP rows, custom reports) lives only in `src/transactions/transfer-payee-label.util.ts`, and `transfer-payee-stamp.guard.spec.ts` fails on a `Transfer to/from ${...}` template anywhere else in `src/`. Migration 161 blanked the legacy-stamped rows; `updateTransfer` heals a surviving stamp to NULL and never regenerates it. That NULL is why the register's Payee sort sinks every transfer to the end in both directions: the column displays a label resolved per read, and an ORDER BY key on the DISTINCT-ids pagination path has to be a stored `alias.property`, never a computed expression. A read surface joining `linkedTransaction.account` for this must mask or restrict cross-owner counterparts the reader cannot read (the account export masks; the custom report query restricts the join to same-owner legs).

The guard also asks what a value _is_ rather than what it starts with, matching its twin in `frontend/src/lib/csv-export.ts`: a value a spreadsheet reads as a number is data, and prefixing one stops the column adding up (issue #1134) -- amounts bypass `escapeCsv`, so the rule covers text columns that can still hold a number (a cheque number written `-123`).

## Scheduled loan interest prices a dated ledger balance, at the moment it is consumed

A scheduled loan installment's interest is `roundMoney(debt * periodicRate)` where **both inputs are dated at that installment's due date**: debt is opening balance plus every non-void, top-level transaction through it (via the shared `LEDGER_MOVEMENT_PREDICATE`, which every balance reader composes so they cannot disagree about which rows count), and the rate is the latest `loan_rate_changes` row effective by then -- never `accounts.interest_rate` alone, which a recorded rate change deliberately does not write, so pricing at it charges a rate nobody pays (`effectiveAnnualRateOn`, truth table shared with the frontend) -- never a value advanced from the previously stored split (money already rounded to 4dp, so the recurrence compounds the discarded fraction) and never `accounts.current_balance` (a through-today read model that excludes future-dated rows). And the stored P/I split is a _template_, not an executable instruction: a principal movement committed between occurrences leaves it stale with no mutation path recalculating it, so the posting path re-resolves the allocation at the consumption boundary (`resolvePostingAllocation`, inside the posting transaction, under the parent lock) and the amortization report anchors its projection on the same due-date-bounded debt (`getLoanProjectionAnchor`). One pricing path -- `resolveInstallmentCore` and the pure `priceInstallment` in `backend/src/loan-installments/price-installment.ts`, which `ScheduledTransactionLoanService.resolveInstallment` delegates to -- serves all three, because each one answered differently is a reported drift. `docs/specs/scheduled-loan-installment-pricing.md` is the spec; INV-LOAN-006 (issue #1253).

The installment is priced at 4dp and **booked in the source currency's smallest unit** (`bookLoanAllocation`): the bank debits cents, so the posted total and interest are rounded to the unit, principal takes the remainder and never exceeds the debt. Any other split template the automatic path posts is booked the same way (`bookTemplateAtMinorUnit`). The Post dialog, the override editor and the template form pre-fill that booking (`bookSplitsAtMinorUnit`, mirrored in `frontend/src/lib/minor-unit-booking.ts` and held to it by `backend/src/common/minor-unit-booking-cases.json`), which the posting path recognises as an unchanged echo; a 4dp line under a cents parent is refused by the split validator (issue #1581).

**The interest line is found by the loan's interest category, so the two never drift apart (INV-LOAN-010).** Every path that writes a template's interest line requires a category the caller owns (`assertLoanInterestCategory`, `src/accounts/loan-interest-category.ts`); there is no name-based default, which found nothing in a translated tree and wrote an uncategorised line the pricing never manages. A change of `accounts.interest_category_id` in `AccountsService.update` moves the line with it through `planLoanInterestRelink` / `applyLoanInterestRelink`, in the same transaction, relinking only a single unambiguous candidate and refusing a change that would leave a managed template unmanaged.

## A pass that settles loan installments walks forward through time, and an import inserts a file's rows in date order

A manual rule run scans the register newest first (`loadCandidateUnits`, `applyRegisterOrder(..., "DESC")`), except when the rule carries a `settle_loan_installment` action: `TransactionRulesRunService.plan()` then asks for `"ASC"`, so the run's rows are the oldest in the window and each is priced on the debt the rows before it leave. The run plans every row before it writes any, so `plan()` threads `priorSettlements` (the settlements planned so far in the pass, none of them written) into the pure planner, which subtracts their principal from the slot's ledger debt and treats their slots as claimed; the preview and the commit fold through the same code and `debtBefore` is in the fingerprint, so a commit whose fold differs from its preview is refused as `PREVIEW_CHANGED`. `applyToNew` (a create, an import row, a bank sync batch) orders its rows by `(transaction_date, created_at, id)`, writes each settlement before the next row plans and drops the loan's cached facts after each write, so there the ledger already holds the earlier settlement and `priorSettlements` stays empty: nothing is subtracted twice, and both paths store the same `debtBefore` for the same rows. The `pricing` record names which path priced it: the import's `debtLedger` is the chained debt with `foldedPrincipal` zero, the run's `debtLedger` is the ledger's and `foldedPrincipal` the chain.

The 1000-row cap (`MAX_RULE_RUN_LIMIT`) stays. A truncated run that settles kept the oldest rows and the preview's `scanOrder` says so (`oldest_first`); to go on past them, run again with `startDate` set to the date of the last row of the page, as `docs/specs/loan-installment-settlement.md` section 14.1 describes: rows of that date the page settled are now splits and are refused `row_has_splits`, so nothing is written twice.

Every import path orders a file's rows by date before it inserts them and before any rule runs, for every user: `orderByDateStable` (`backend/src/common/date-order.util.ts`) in the QIF, OFX and CSV loops of `ImportService`, in `eligibleImportRuleIds` for a Money file, and over the created rows of a bank sync before its rules batches. The sort is stable, so rows of one date keep the file's order and their `created_at` spacing still reflects it; the import's messages name a row by its place in the file. Bank sync also returns the accounts a rule moved money into (`affectedAccountIds`) and dispatches their net-worth recompute after its commit, as it does the synced account's. INV-RULE-005, INV-CACHE-001; `docs/specs/loan-installment-settlement.md` sections 7.2 and 14.

A QIF split line that transfers into another account writes its leg in that account's currency (A26-M18, MON-M27, MON-H11 QIF half): `ImportRegularProcessorService.splitTransferLeg` converts it at the stored rate for the row's date through `resolveFxRateOrNull` and `applyFxConversion`, stores the rate on the leg and flags it with the plain transfer path's `PENDING IMPORT` note, since the market rate is not the bank's. With no rate the row is refused through its savepoint and the import result names the pair; a 1:1 leg is never written (INV-FX-001). `test/integration/import-qif-split-transfer.integration.spec.ts`.

## An API create names its own row, and a bulk create is many single creates

A client moving its own data in through the API (issue #1713) needs two things the register does not: to send a batch in one request, and to retry a create whose response was lost without making a second row. Both are built from the single-row create rather than beside it.

**`externalId` is the caller's key for a row, unique per account.** `POST /transactions` and `POST /transactions/transfer` take an optional `externalId` (`transactions.external_id`, `VARCHAR(255)`). A create that repeats a key already used in the account returns the row that holds it, as it stands: the key names the row, so a retry carrying a different body does not edit it, and the rules, balance, history and recalculation of the original do not run again. The single-row routes answer a repeat with 200 rather than 201, so a client can tell a retry's answer from a new row. A transfer stores the key on its source leg only, and a key held there by anything other than a transfer leg linked into the requested destination account is refused with 409 rather than answered with a row that is not the caller's transfer. A transfer retried from the caller's own source account is answered before `prepareTransfer` (`findOwnTransferByExternalId`), so a committed transfer is not re-validated and its rate is not resolved again; the lookup reads only the caller's own rows, so it answers nothing authorization would have refused, and a cross-owner source leg is found inside the write instead. A plain create does not refuse a key held by a transfer leg: a `convert_to_transfer` rule turns the row a plain create wrote into one, and its retry must still be answered. The key is not editable (`UpdateTransactionDto` omits it), and `GET /transactions?externalId=` finds a row by it, as a register content filter (`RegisterRowFilters.externalId`); an empty value is refused.

The guarantee is the partial unique index `idx_transactions_account_external_id` on `(account_id, external_id) WHERE external_id IS NOT NULL`, the shape bank sync's `bank_sync_imported_transactions(account_id, external_key)` already uses. The lookup each create makes before its insert is advisory (CONC-002): two creates racing past it both insert, the index refuses the second, and that path catches the violation by the index's name (`isExternalIdConflict`, `src/transactions/transaction-external-id.ts`) and answers with the winner. It does so only outside a caller's transaction, which the violation has aborted. The key is the caller's identity for the row, such as the bank's own transaction id; a client that mints a fresh key per attempt gets no protection, which is section 6 of `docs/concurrency-and-idempotency.md`. Two paths take a key away from the account it was created in, and a retry there makes a second row (INV-API-001 is `partial` for them): undoing a delete restores the row without its key, as it restores it without its foreign-currency entry, because the undo snapshot (`snapshotTransaction`) is an explicit list of columns; and an edit that moves a keyed row to another account takes the key with it.

**An OFX import keys each row by the bank's id.** `parseOfx` reads the row's `FITID`, and the regular import processor stores it as `externalId` under the prefix `ofx:` (`ofxExternalId`, `src/import/ofx-external-id.ts`); a row without one, or whose key would not fit the column, imports as before. Some banks give several rows the same `FITID`, so the parser leaves out an id that two rows of one file share (`dropRepeatedFitIds`). Before the first row, the import reads which of the file's keys the account already holds, in one lookup per thousand keys (`loadHeldExternalIds`), and adds each key it writes, so the rest of the file sees it. A row whose key the account holds is skipped only when the row holding it has the same date and amount; otherwise the bank reused the id, and the row imports without a key. A skipped row writes nothing and is decided before the transfer check, though it still takes its turn in the per-signature transfer count, without querying. A row someone edited to another date or amount no longer matches, so a later download of it imports again. A transfer row with a key does not use the count, which depends on where the row sits in the file: it takes over its key on a transfer of the same signature that the account recorded before this import and that has no key (`adoptKeyOnRecordedTransfer`, `src/import/import-transfer-dedupe.ts`) and is skipped as that transfer. That is how the other account's statement finds the leg the first import created, and how a transfer imported before keys existed gets its key; with no such transfer it is checked only as a leg of a Quicken merged split, so it imports whatever its place among identical ones already keyed. The update is conditional on the row still having no key, so two imports cannot both take it. The lookup is advisory here too: an insert the index refuses fails inside the row's own savepoint, so the import loop rolls back to it, puts back the result counters the row raised (`restoreRowCounters`), and counts the row as skipped, not as an error. The first 50 skipped rows, for this reason or as a duplicate transfer, are listed in `ImportResultDto.skippedRows` with their date, amount, currency, payee and reason (`recordSkippedRow`, `src/import/import-context.ts`); that function is the only place that raises `skipped`, which keeps the full count, so the list is always its first rows. The prefix makes a clash with a key an API client chose unlikely, not impossible: an API key is free text. The undo-of-delete gap described above applies here as well: a restored row comes back without its key, and the next download of it imports a second copy.

**A bank-sync duplicate key is a function of the bank row, never of the other rows of the fetch.** `keyFor` (`src/bank-sync/bank-transaction-planner.ts`) keys a row by its entry reference with its date and signed amount (`ref:<reference>|<date>|<amount>:<occurrence>`), so a reference the bank repeats on a later transaction is a new key and the earlier row keeps its own when a later fetch holds both; a key decided from which rows share the fetch re-keys the earlier row on the next sync and imports it twice (A26-H09). The writer and the preview ask the ledger the same question through `findHeldRows` (`src/bank-sync/bank-sync-plan-fingerprint.ts`), which also reads the keys written before that fix. INV-BANKSYNC-001; `docs/specs/bank-sync.md` section 6.

**`POST /transactions/bulk` is the single-row creates in a loop** (`TransactionBulkCreateService`, at most `BULK_CREATE_MAX_ITEMS` rows). Each item carries a `transaction` or a `transfer`, the bodies the single-row routes take, and is created through the same service call, joint-account routing included. Each row commits on its own, and one that fails is reported in its result with the status and message the single-row route would have answered, through the same mapping the global filter uses (`httpErrorBody`, `src/common/filters/http-error-body.ts`), without undoing the rows before it. One transaction around the batch would buy nothing the key does not already give: with keys, a batch whose response was lost is sent again and its committed rows come back `existing`. It would also run every row's post-commit work (net-worth recalculation, loan template repricing) inside the batch rather than after each commit (INV-CACHE-001). Rows are written in date order through `orderByDateStable`, as every import writes its rows, so a rule settling loan installments folds forward through time; the results are still reported by the request's index. A shape error in any item, including an item carrying neither or both of `transaction` and `transfer`, fails the whole request with 400 before any row is written, because validation runs on the body. The cap is small because rows are written one after another, each with its own lookups, rules and read-back, and a full batch has to finish inside a proxy's request timeout; a client should still give every row a key, so a batch that did time out can be sent again. The route is not delegable.

INV-API-001.

## A category's leaf name is not its identity

"Cell Phone" under **Bills** and under **Business** is an ordinary chart of accounts, so a bare leaf name identifies nothing. Both halves go through `categories/category-name.util.ts`:

- **Emitting**: `qualifiedCategoryName` / `loadQualifiedCategoryNames` produce `"Business: Cell Phone"`. Analytics groups on `SPLIT_CATEGORY_ID` and resolves the label from the map -- there is deliberately no category-_name_ SQL fragment left, and `transaction-split-query.util.spec.ts` fails if one reappears.
- **Accepting**: `resolveCategoryNamePaths` matches a name the model sends back, separator- and spacing-insensitive, and **refuses an ambiguous one** with the qualified candidates rather than picking a winner.

The test that matters is the round trip: every name we emit must resolve back to the category we emitted it for (`category-name.util.spec.ts`) -- four hand-rolled resolvers had drifted apart, and one rejected the exact spelling every tool description tells the model to type, falling through to a last-segment fallback that silently read the _other_ "Cell Phone".

Also: `Uncategorized` (the user filed it nowhere) and `Unknown category` (we could not resolve the name of the category they did file it under) are different facts with different constants. Do not fold the second into the first.

## A category filter names a type with a pseudo-id, never with the type's ids

`categoryIds` (`parseCategoryIds`, `common/query-param-utils.ts`) accepts four pseudo-ids beside UUIDs: `uncategorized`, `transfer`, `income` and `expense`. The two type pseudo-ids resolve inside `getAllCategoryIdsWithChildren` (`common/category-tree.util.ts`), the one helper every category predicate already expands its ids through, so no predicate site enumerates a type and none needs to know the two type pseudo-ids exist. A client that listed a type's ids overflowed the request line at a few hundred categories (`docs/frontend/api-and-cache.md`, "A filter the server can apply is not a list the client enumerates").

## A money value carries the currency it was calculated into

Not the currency of the account it is filed under. `InvestmentTransaction.exchangeRate` converts a trade into the _settlement_ account's currency (the funding account when named, else the brokerage's linked cash account), so a PLN brokerage funded from EUR holds a EUR cost basis. The amount and its currency travel together (`ReplayedLot.currencyCode`), and a consumer compares that field against what it is reporting in. A mismatch is **unknown**, not a conversion -- today's rate answers today's question, not the acquisition's -- and two acquisitions settled in different currencies cannot be summed at all.

## A currency a user's action needs is that user's, never everybody's

`currencies` is one table for every user, and `findAll` lists each user every active row with no creator, so a row a request writes is offered to every tenant unless it is written for the requester. A request path (the default-currency preference, the Money import, the `findAll` fallback) calls `CurrenciesService.ensureCurrencyForUser(userId, code)`: a known ISO 4217 code (`isKnownIsoCurrency`) becomes an inactive reference row, any other code the user's own currency, and only the user's `user_currency_preferences` row is activated. The active system insert is private to the bootstrap of the default currency; `ensureCatalogCurrency` stays for the bond catalog. The ensure runs inside the transaction that writes the reference, before it: `user_preferences.default_currency` has a non-deferrable foreign key, and an ensure after the commit refused every first default but USD on a fresh instance (A26-M25). A user's deletion locks the currencies they created, then removes those nothing references (`lockCurrenciesCreatedBy`, `removeUnreferencedCurrencies`); the trigger `currencies_creator_cleared_deactivate` deactivates any that lose their creator on another path, so none becomes an active system currency (A26-M17). A request DTO validates a code with `@IsCurrencyCode()` after upper-casing it, and the entity never serializes `createdByUserId`. INV-CURRENCY-001.

## A fallback answers only the question it was asked

A lookup that fails is a fact about _that_ lookup. A stale scenario id says nothing about the user's other scenarios, so an empty report hardcoding `strategies: []` made a second claim without looking -- and took away the switcher that was the only route back. Fall back to the default rather than to nothing, and fill the surrounding fields from a real read. And a retry has to change something: recursing with the same id after establishing the id is gone is a comment claiming a recovery that cannot happen.

## Money investment mapping is finalized after both mappers run

`mapInvestments` cannot know whether `mapTransactions` will preserve or collapse a cash split. Reconcile generated investment companions only after cash-source mapping: when a redemption remains embedded, its preserved sibling is the interest record, so the generated companion and mutual link must not be written as a second representation of that income.

## A behavior promised "when a filter is active" keys off the filter itself, carried explicitly on the command -- never off a transport detail that sometimes coincides with it

Bulk update keyed its split-line restriction off `mode === "filter"`, but hand-picked rows ship as mode `ids`, so the filter silently stopped applying. The client sends the active filter as its own field in both modes (`BulkUpdateDto.categoryFilterIds`) and the server restricts on that; regression tests assert the ids-mode payload carries it and honors it.

## What a category cost is its debits NET OF its credits

A refund, return, chargeback or cashback filed against an expense category is a debit that came back, so it belongs in that category's total. Every surface that reached for the gross (`WHERE amount < 0` + `SUM(ABS(...))`, `if (amount >= 0) return`, `summary.totalExpenses` alone) disagreed with the register's own balance for the same filter (issue #1125). Sum the signed amount over rows of **both** signs, per category, and decide what the row _is_ from the net: `isNetSpending` and `NET_SPEND_AMOUNT` (`backend/src/built-in-reports/spending-reports.service.ts`) on the server; `netEntityTotal` (`frontend/src/components/transactions/widget-shared.ts`) for a summary scoped to one category. Never take `totalIncome` or `totalExpenses` alone as a category's headline -- those are a register's in/out split.

Dropping the sign filter means income now reaches the aggregate and has to leave by a different door: a bucket whose net is not spending is not a row in a spending report -- one predicate, not a per-call-site `> 0`. Netting is **within** one category, never across two; both halves come from the same filtered aggregate. (The payee surfaces are deliberately unchanged: `PayeeInfoWidget` prints received credits as their own line beside the spend, so netting them into the headline would count them twice.)

The custom report engine (`backend/src/reports/reports.service.ts`) follows the same rule for every grouping: each line lands in a (group, category) cell, signed, and a cell counts only when its net is in the report's direction, so a refund lowers its category under `EXPENSES_ONLY` and `BOTH` shows the magnitude of each category's net, never the sum of row magnitudes. A transfer is not a category and is not netted; the `NONE` metric (the row list) keeps its row-level direction (INV-REPORT-004, audit A26-M33).

## A budget's actuals honour the budget's own settings, on every surface that reads them

A budget's spent figure is one query, `queryCategorySpending` (`backend/src/budgets/budget-spending.util.ts`): the live page, the alerts and the period close all read it, so a close freezes the figure the page showed. It reads the budget row itself (currency and `config`), so what the budget wizard chose cannot be lost between a caller and the query: the accounts in `config.excludedAccountIds` (`budgetExcludedAccountIds`) are out of every actuals query through `excludeBudgetAccounts`, applied after the builder's `.where(...)`, and out of the source side of the transfer builders (`OutgoingTransferWindow.excludedAccountIds`). The budget report services apply the same helper to their own queries. The generator's history analysis runs before the wizard's exclusion step and does not apply them (audit A26-M31).

Closing a period writes what `computeRollover` computes, which needs `periodCategories.budgetCategory` loaded: a fixture that hydrates the relation by hand hides its absence, so the close is held by a PostgreSQL case (`backend/test/integration/budget-period-close.integration.spec.ts`, A26-M32). The next period is the month after the closed one (`getFollowingMonthPeriodDates`), never the wall-clock month, so a close before the period ends leaves exactly one OPEN period (A26-L38). A flex-group warning is budget-wide, so the group in `data.flexGroup` is part of `idx_notifications_fingerprint` and of `deduplicateAlerts`: two groups over 90 percent are two alerts (A26-L39).

## A transfer leg becomes a Sankey flow by scope and class, never by its category

The Cash Flow Sankey (`backend/src/built-in-reports/cash-flow-sankey.service.ts`) reads a transfer leg only when its own account is in the report's scope and its counterpart is not: the whole-transfer query takes the counterpart from the linked row's account, the split query from `transfer_account_id`, and both put `NOT (... = ANY(scope))` in SQL so the two legs of an internal transfer are never read (SANKEY-002). The counterpart's account type decides the class (`classifyCounterpart` in `cash-flow-sankey-assembly.ts`); a credit card is never debt. Every branch carries `investmentExclusionSql` and the VOID predicate (`sankey-branches.guard.spec.ts`, SANKEY-003), and the closing identity is checked in scaled integers before a response leaves (SANKEY-001). `docs/financial-semantics.md` section 2 has the rules.

## A calendar day's TOTAL is its own read model, and it is two halves of one series

`GET /accounts/daily-balance-totals` (`accounts/daily-balance-totals.service.ts`) answers one question `GET /accounts/daily-balances` does not: what the accounts in scope are worth together, in one currency, on each day of a month. Its history half is `AccountsService.getDailyBalances` and its projection half is `BalanceForecastService.getBalanceForecast` per account; it computes no balance itself, and `currentBalance` is read on neither side, so both halves stay ledger sums under `LEDGER_MOVEMENT_PREDICATE` (INV-BALANCE-001).

Four rules make the two halves one honest series, and each one exists because its opposite is the plausible mistake:

- **Actual or projected is the SERVER's day.** The response carries `today` and the client compares against it. A browser west of the server rolls over hours later, so a cell that consults its own clock captions a settled day a projection.
- **A projected day is priced at TODAY's rate, a history day at its own.** The day a projection is about has no rate yet; reaching for the nearest one would report a forecast at a rate nobody struck. One rate index (`common/time-series/rate-index.util.ts`, shared with `NetWorthService`) answers both.
- **A single-currency scope converts nothing and reports in its own currency**, not in the reader's preference. That is what makes one account's calendar agree with its own register's balance column to the cent, and it is why `missingRatePairs` is always empty there.
- **An account that cannot be answered is an unknown component, never a smaller total.** `FxAggregate.addUnknown()` carries an account whose forecast was withheld whole (`BalanceForecastService`'s rule, issue #1247) or that this caller cannot project at all -- today, a joint account, whose forecast belongs to its owner's identity and which the response names in `forecast.unforecastableAccountIds`. The day's `total` is then `null` with `knownSubtotal` holding what WAS known, which may only be printed under a caption that says it is partial.

**The projection half does not annotate overdue occurrences.** `getBalanceForecast` carries an occurrence that fell due and was never posted or skipped onto tomorrow (discussion #1784), and this read model takes its `points` and drops its `overdue`, so a calendar day total can step down on tomorrow with nothing saying why. That is a known gap, not a rule: summing `overdue` per scope into the response is the fix when a surface needs to explain the step.

The date range is bounded by `CALENDAR_RANGE_MAX_DAYS` (`common/validators/calendar-range.validator.ts`), which every calendar DTO reads so the cap cannot drift apart per endpoint: an unbounded range walks a per-day series over every account in scope and asks the forecast to expand every schedule to the horizon.

## The register's sort field is a list, not a string, and only one query may order by a joined column

`GET /transactions` takes `sortBy` and `sortDirection`. The fields it accepts
are `TRANSACTION_SORT_FIELDS` in `backend/src/transactions/register-order.ts`,
which is also what the browser's column headers and the AI and MCP tools'
enums derive from, so a column a reader can click is a column every caller can
ask for, with a contract spec holding the browser's copy equal to it.
`parseTransactionSort` (`backend/src/transactions/register-sort-param.ts`) is
the boundary: `assertStringParam` first, because Express hands a repeated key
over as an array whose `includes` compares whole elements, then a
case-insensitive match that returns the list's own spelling -- lowercasing the
input and testing that against the list silently rejects `refNumber`, the one
field whose name is not all lower case.

`registerPrimaryOrder` maps a field to its ORDER BY term, and it **throws**
for `account` or `category` unless the caller passes that table's join alias.
Only the register query joins those tables; the three queries that sum the
rows newer than a page select from `transactions` alone and pass no aliases,
so none of them can be ordered by a column its statement does not have. Two
shapes the map may never take, both forced by how TypeORM pages a query with
joins (it selects DISTINCT ids plus the order columns from a subquery and
rewrites each order key by splitting on the dot): the term is always
`alias.property`, never a computed expression -- which is why status orders by
its stored value rather than by a lifecycle rank -- and never a one-to-many
alias such as `tags`, which would emit an id per joined row and repeat
transactions on a page. Nullable text columns take `NULLS LAST` in both
directions, because a blank payee is the absence of a value rather than the
smallest one. Under any field but the date, the transaction date becomes the
second key, so one payee's rows still read chronologically instead of in the
order an import happened to write them.

## A running balance is summed over the rows the register shows, and a deep link is counted over them too

`RegisterRowFilters` (`backend/src/transactions/transactions.service.ts`) is
the one shape naming everything that narrows the register, and
`buildFilteredIdsSubquery` is the one query that applies it. Both the running
balance's zero-based total and the page a `targetTransactionId` lands on are
computed over that set, because both are answers _about the rows on screen_:
a balance summed over a wider set counts rows the reader cannot see, and a
page counted over a wider set does not hold the row it was following.

Four filters used to narrow the listing without reaching either -- status,
entry currency, attachment presence and the KEY:VALUE tag filter -- along with
the brokerage exclusion, and a register narrowed by any of them fell through
to the unfiltered regime: the account's whole projected balance, walked down
past rows that are not the ones being shown. A filter added to the listing is
added to `RegisterRowFilters` in the same change: every member of that shape
is required rather than optional, so a new field is a compile error where the
shape is built until it is named -- and that is the moment to apply it in
`buildFilteredIdsSubquery` too, which the type cannot check for you. The
uncategorised pseudo-category is the example of getting the second half
wrong: the listing matches a split parent through its children, and an arm
that matched only the plain rows gave one row two different balances
depending on which way the register ran.

The page count also has to ask the register's ORDER, not an approximation of
it: all four keys, with the amount leg running opposite to the list (the same
credits-before-debits rule `applyRegisterOrder` applies), and the target's
keys read out as text. `created_at` is stored to the microsecond and the
entity reads it into a millisecond `Date`, so binding that value back compared
a row with a truncated copy of itself and counted it as being above itself.
The one predicate that still differs is the `uncategorized` pseudo-category,
which the subquery reads more narrowly than the listing does; its own comment
says why.

## A stored holding is a projection of the ledger, never an accumulator

`holdings.quantity` and `holdings.average_cost` are derived, and the ledger they are derived from is `investment_transactions`. They used to be maintained incrementally -- each acquisition blended into the stored average as it arrived -- which makes the stored figure a function of **insertion** order. Insertion order is not economic order: BUY 100 at 10 dated January, BUY 100 at 20 dated March, then a SELL 50 dated February entered third, and the blend gives 15.0000 while the replay gives 16.6667 (issue #1388). `lockHoldingScope` could not have caught it; it serializes writers, and this is one writer's arithmetic.

So no path writes those columns from a delta. Every investment-transaction write -- `create`, `update`, `remove`, `updateStatus`, `applyParentStatusToEmbeddedRows`, `createEmbeddedForSplit`, `reverseAndRemoveEmbedded`, `transferSecurity`, and `updateLinkedTransfer` -- finishes by calling `HoldingsService.rebuildScopesFromTransactions(userId, scopes, manager)` for the `(accountId, securityId)` pairs it touched, **inside the same `withScopedDb` transaction as the ledger write** and under the same advisory lock, so the projection commits or rolls back with the rows it describes. An edit passes the OLD pair as well as the new one, a delete passes the pair it removed rows from, and the rebuild runs AFTER the ledger write is final -- `reverseTransactionEffectsInTransaction` deliberately does not carry it, because it runs before the row is re-saved or removed and would read a ledger that still contains the old values. A QIF/CSV/OFX import rebuilds the whole imported account once per block (`ImportService.rebuildImportedHoldings`) rather than per row: an import arrives in file order. Undo/redo already rebuilt per account and still does. `POST /holdings/rebuild` is unchanged and is the repair for rows written before this rule; there is no versioned-recompute hook to hang it on.

Economic order is `INVESTMENT_REPLAY_ORDER` (`securities/investment-replay.util.ts`): `transaction_date`, then `created_at`, then `id`. The `id` leg is not decoration -- rows written by one import or one split transaction share `created_at` to the microsecond, so without it two replays of the same unchanged ledger may relieve basis in different orders and store two different averages. `INVESTMENT_REPLAY_ORDER_SQL` is the same order for a raw `SELECT`. Every query that folds `investment_transactions` into a position uses one of the two -- the net-worth replays, the daily-movement replay, the investment-report replay and the account-balances positions included -- and `investment-replay.guard.spec.ts` fails a hand-written `ORDER BY ... transaction_date` or `order: { transactionDate }` without the `id` leg in any file that reads the ledger. `applyRegisterOrder` is the **display** order of a register and is not this: it answers "what does the user see first", not "what happened first".

Two things the projection does not fix, stated rather than smuggled in:

- **An unpriced acquisition adds shares and no basis.** `acquisitionCost` returns `null` for a row that cannot say what it cost, and `computeHoldingsMap` skips it rather than booking a free lot -- so the average cost it produces is a partial figure and the column has nowhere to say so. Surfaces that must not print a partial basis as a total derive completeness from the ledger themselves (`docs/financial-calculation-contract.md`).
- **A scope with no ledger rows projects to "no holding"** and its row is deleted, which is what `POST /holdings/rebuild` has always done. An imported opening position is an `ADD_SHARES` row; a holding with nothing behind it is residue.

## Accounting basis and reporting provenance

Accounting reads use `backend/src/accruals/reporting-basis.ts`: an enabled user's explicit cash/accrual request wins over their default; an omitted preference defaults to cash. Disabling accrual forces cash execution even for a remembered or explicitly requested accrual basis, while preserving schedules and source-edit maintenance. An accrual selection with no relevant schedules uses native SQL without changing the selected-basis label. Fixed cash reads reject incompatible overrides at their transport boundary. `ReportingEndpoint` declares and validates the choice, returns `X-Reporting-Basis` for array responses, and names the result currency when the reader supplies one. A custom report accepts basis in its execution body or query; conflicting values are refused. Bank balances, reconciliation, account CSV/QIF exports and anomaly detection remain cash-specific. The register can show source-linked recognition rows under Accrual.

Assistant and MCP report generation call `BuiltInReportsService.getLlmReport` and return the same `{type, basis, currency, fxComplete, result}` envelope, including net-worth arrays. Budget status and period comparison accept basis through their shared domain readers. A reporting failure carries only whitelisted repair metadata through REST (`reporting`) and agent errors; generic 5xx internals remain redacted. Anomaly `months` is the history window, separate from the statistical threshold.

The component reader in `backend/src/accruals/reporting-details.ts` reads persisted allocation components through explicit invoker relations, using native source SQL for Cash. It preserves source transaction/split/schedule IDs, cash and recognition dates, native amounts and conversion provenance. Ordinary components exclude transfer and investment linkage through the shared predicates. Category filters expand descendants through the canonical category tree helper. Missing FX withholds the converted total and retains native totals and a named known subtotal. Over-limit requests refuse; they never present a truncated sum as a total.

Hydrated reporting copies retain a separate virtual report identity and original source/backlink identities. Their `reportingProvenance.readOnly` flag distinguishes them from writable bank entries. Transfer and investment references join through virtual identities while SQL runs, then return original identities for source drilldown. Reporting copies are never persisted.

The custom-report export returns a versioned JSON artifact and spreadsheet-safe CSV from the same selected-basis execution, repeating basis/currency/completeness and row provenance in the CSV. It does not alter account-register exports. Accrual routes remain inactive until the planned release; these contracts describe the isolated implementation awaiting GUI and release acceptance.

Transaction analytics summary and monthly headline figures are in the user's reporting currency, converted per cash or recognition component before aggregation. Summary `byCurrency` values and explicitly currency-labeled grouped/tag/account rows remain native; never add those native buckets to reconstruct a display-currency headline. Assistant/MCP transaction summaries and grouped amounts use the same dated reporting conversion. Source transaction counts deduplicate split components within the selected basis. Missing history refuses a combined figure with the reporting repair payload.

Historical budget-tool requests use the requested calendar month and its saved effective plan when a period snapshot exists, while recomputing selected-basis actuals. Without a snapshot they use the current configured plan for that month. Current velocity/health are omitted from historical answers. Stored period records, account balances/registers, category/payee source-identity cards, investment performance and weekday cadence remain explicitly cash-specific; category/payee spending-over-time uses the separate accrual-aware analytics endpoints.

The accrual GUI discovers schedules through the owner-only source lookup before fetching a selected schedule's detail. The lookup authorizes source identity even when no schedules exist; it does not expose another owner's existence or allow acting delegates. VOID sources remain discoverable for removal. The preferences PATCH accepts only `cash` or `accrual` for `reportingBasis`, writes that column alone, and rejects null/arrays. GUI support does not register the accrual controller in production AppModule; activation stays with the reviewed release.

## Cash list completeness and accrual net worth

The LLM cash-list adapter requests native currency buckets for counts and breakdowns; its reporting totals are folded independently through `FxAggregate`. Ordinary cash summaries and transfer rollups still convert their headline amounts. Account net-worth summaries preserve their existing nullable totals, known subtotals and missing-pair flags in both bases. Full accrual net-worth reports retain their dated missing-FX refusal; only the latest-value adapter requests incomplete components for the account summary to classify. The integration suites `llm-analytics-currency.integration.spec.ts` and `net-worth-completeness.integration.spec.ts` pin those contracts.
