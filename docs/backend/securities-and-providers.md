# Backend: securities, prices and outbound providers

What a stored price row means, daily-series integrity, history depth, and how every outbound provider call goes through the circuit breaker and is logged once. Read this before touching `src/securities/`, a price writer or any `fetch` to a third party.

Paths beginning with `src/`, `test/` or `scripts/`, and layer configuration filenames, are relative to `backend/`; other source paths are relative to `backend/src/`. Explicit repository prefixes are preserved. `backend/CLAUDE.md` is the short index; this document is where the reasoning lives.

## A stored price says which session it belongs to, not which minute it was fetched

`security_prices` holds one row per trading day, and that row is the **session**: official close, full-day volume, high/low, adjusted close. A live quote (`regularMarketPrice`) is a true statement about 14:42 and a false one about the day -- and the frontend auto-refreshes quotes through the session (`usePriceRefresh`), so a row for today exists long before the day is over. Three rules, each with a test:

- **"Has a price for today" is not "the day is settled".** Ask whether the *session* has ended -- `isSessionSettled` (`providers/settled-bar.util.ts`), on the market's own clock in the market's own zone, from the stored `market_timezone` / `market_close_time`. Never from the presence of a row or the server's clock.
- **The closing job settles the day from the daily bar, after the quote refresh.** `settleDailyBars` re-reads a bounded recent window and upserts the bars whose sessions have ended, so a missed run or provider outage repairs itself. The quote is what a still-open market can offer; the bar is what the finished session did, and the bar wins.
- **A calculated column needs a writer on the recurring path.** `adjusted_close` was populated only by the on-demand backfill, and because `loadPriceSeries` picks one basis per series and keeps only adjusted rows, that silently truncated every return series at the last backfill date. The quote path fills `adjusted_close` with the close it is writing -- definitional for the newest session (adjustment factor 1), but only where the series already carries an adjusted close; both conditions live in the `CASE ... EXISTS` inside the statement (an MSN-priced series given exactly one adjusted close flips `bool_or(...)` and collapses to that row).

A daily bar is not a quote, so settling clears `quoted_at`; and a `source = 'manual'` row is a user correction no provider write may overwrite -- the quote path and `bulkUpsertPrices` both carry `WHERE security_prices.source IS DISTINCT FROM 'manual'`, and the quote path treats the refusal as a successful no-op that reads back the winning row. The honest cost: a manual row on a provider-priced security has no adjusted close, so that day stays out of the adjusted series.

Related: **a bar's timestamp is the instant its session opened, so the day it belongs to is the exchange's calendar day.** `barDate` reads it in `meta.exchangeTimezoneName`, falling back to UTC; `setHours(0,0,0,0)` made `price_date` a function of the container's timezone.

## A price is a number in a currency, and only one side of that reaches the row

`security_prices` stores the number; the currency it is read in is
`securities.currency_code`. So the two have to be checked against each other
before the write, or a provider that answered about *another listing of the same
ticker* -- the LSE line of a US stock, a GBP share class of a USD fund -- writes
numbers understated by the exchange rate on every row, with nothing in the stored
series to show it. The exchange is not the answer either: a USD-denominated ETF
on the LSE is exactly the case an exchange guess gets wrong, which is why
`QuoteResult.currencyCode` exists and is read from the instrument.

**The comparison is one function.** `verifyProviderCurrency`
(`providers/quote-currency.util.ts`) normalizes both sides with
`normalizeQuoteCurrency` -- trim, upper-case, GBX/GBp to GBP -- and returns
accepted-and-verified, accepted-but-unverified, or refused.
`SecurityPriceService.refuseForeignCurrency` is the only caller shape: it returns
the `tr()` message to report, or `null` to proceed. Normalization is a comparison
and not a second conversion: both providers already divide pence into pounds
(`convertGbxToGbp`) before returning bars, so the function is idempotent and
"GBP" in gives "GBP" out.

**A historical payload carries its own metadata, because an array cannot.**
`fetchHistoricalSeries` (and the optional `fetchHistoricalWindowSeries`) return a
`HistoricalSeries` -- `prices` plus the `currencyCode`, provider symbol and
exchange the provider named -- and that is what every path writing into
`security_prices` calls. Yahoo's and MSN's `fetchHistorical` survive as
prices-only wrappers for the two callers that have no security to verify against:
the FX pair series and the market-index series. The bundle preserves the
load-bearing distinction the callers already depended on: `null` is no answer,
an empty `prices` is an answer with no bars.

**Where the check runs, and why it is not one place.** The shared acceptance
points are `fetchQuoteWithFallback` and `fetchHistoricalWithFallback`, where a
provider whose currency disagrees is *passed over* rather than accepted -- the
next provider gets its turn and faces the same check, and the last refusal is
what the caller reports. `fillPriceWindow` reaches `bulkUpsertPrices` through
neither, so it is an acceptance point of its own. And the group paths --
`refreshAllPricesGlobally`, `backfillHistoricalPrices`, `settleDailyBarsGlobally`
-- fetch once for a representative and write for every security sharing its
symbol and exchange, while `groupKey` holds no currency: a second user's row for
the same ticker can be recorded in a different currency and only one of them can
be right about the answer. So the check runs again per security immediately
before each `savePriceData` and `bulkUpsertPrices`, quietly (the fetch path has
already logged what it had to say).

**A group fetch is judged on the group, never on its representative.** The three
group paths pass the whole group into `fetchQuoteWithFallback` /
`fetchHistoricalWithFallback`, which accept the answer as soon as *one* member
could store it (`acceptedBySomeMember`). Judging the fetch on the representative
alone meant one user's mis-recorded currency marked every other holder of that
ticker failed, although the answer was storable for all but one of them. The
per-security check at the write is what decides who gets the answer; the fetch
only decides whether to keep looking for a provider.

**Unverifiable is accepted with a warning, and that is a decision, not an
oversight.** MSN's chart series reports no currency at all, so refusing every
silent provider would leave MSN-priced securities with no prices; the same goes
for a security with no recorded currency. Those store with a logged warning. What
this does not buy is auditability of what is already stored: a price row does not
record the currency it was written in, so rows written before this check cannot
be told apart from the database. That would be a column on `security_prices` and
a migration.

`fetchAuthoritativeCurrency`, which corrects the exchange-guessed currency at
security-create time, reads the same `normalizeQuoteCurrency`, so the currency a
security is created with is comparable letter for letter with the one every later
answer is measured against. INV-PRICE-001.

## A cryptocurrency is a Yahoo pair whose currency is its fiat leg, priced every day

A coin is a security with `security_type = 'CRYPTO'` whose symbol is Yahoo's `<COIN>-<FIAT>` pair, stored whole (`BTC-EUR`); its currency is the fiat leg (`EUR`), because that is the currency every price Yahoo answers for the symbol is quoted in. Every provider's lookup gives a result it typed `CRYPTO` its exchange and currency from one helper, `cryptoLookupFields` (`securities/providers/crypto-pair.util.ts`): the currency the provider reported, else the fiat leg (`cryptoPairFiat`), else `null` (unknown), never an exchange or country guess; the exchange guess it replaces read every dotless symbol as USD, so a EUR pair was saved as USD and every one of its prices was refused by `verifyProviderCurrency` (INV-PRICE-001, issue #379). The exchange is the canonical `CRYPTO` (`SECURITY_EXCHANGES`), not Yahoo's `CCC`; it has no `EXCHANGE_TO_COUNTRY` entry, so a holding falls in the geographic rollup's Other bucket, and `getAlternateSymbols` tries no `.TO` / `.V` / `.CN` listing for a security whose exchange is `CRYPTO` or the legacy `CCC` (`isCryptoExchange`), keyed on the exchange rather than the symbol's shape, because `BTC-USDT` has no ISO last leg and a hyphenated listing can have one. A coin trades every day and its Yahoo session is the UTC day, still open at 17:00 New York, so each closing run settles the previous UTC day's bar and stores the current day's quote as provisional; besides the weekday closing job a weekend run (`scheduledWeekendCryptoRefresh`, `docs/cron-jobs.md`) refreshes and settles the securities of that type only, so Saturday's run settles Friday, Sunday's settles Saturday and Monday's settles Sunday; it selects on `security_type` rather than the exchange, because a coin created before the lookup named `CRYPTO` still carries `CCC`.

## A bond-linked security is priced by the bond engine, never by a provider

A security with `bond_program_id` set (`docs/specs/polish-retail-bonds.md` section 12, `docs/specs/bond-program-securities.md`) has one automatic price source, `BondPriceService` (`source = 'bond_engine'`). Every path that asks a quote provider about a security -- the quote refresh, the selected refresh, the settlement, both backfills, the on-demand report fill and the intraday chart -- asks `isPricedByQuoteProvider` (`securities/provider-priced.util.ts`) first, directly or through `isRefreshEligible`; `provider-priced.guard.spec.ts` fails a new path that does not, and a forced backfill ignores `skipPriceUpdates`, never the link. A manual price always wins and the engine never replaces it; the engine row replaces every other row on its days (provider rows and transaction-derived rows alike, because a transaction-derived price is one lot's trade price, not the holding's value), and a transaction-derived price never replaces a `bond_engine` row. Engine rows store `adjusted_close` NULL (coupons are recorded as INTEREST income, the close is the value), and a manual price written over an engine row does not inherit one. The check is repeated at write time: both provider upserts (`savePriceData`, `bulkUpsertPrices`) insert nothing for a security that is linked when the statement runs and never replace a `bond_engine` row, so a refresh that loaded the security before it was linked cannot write a provider price for it. Unlinking (link set to null or another program) deletes the security's `bond_engine` rows in the same transaction, under the per-security recompute lock (`docs/cron-jobs.md`), and clears the series its transactions name outside the new program (`clearForeignSeries`). The link is refused unless the program's currency equals the security's (INV-PRICE-001), and a linked security's currency cannot change while it stays linked. The engine's unit price is the blend over the lots of every series the security holds, each valued by its own series' terms. INV-BOND-005.

## A program-linked security's transactions name their series

One security holds a whole bond program (EDO), so each share-moving transaction states the series it acts on (`investment_transactions.bond_instrument_id`). `resolveTransactionSeries` (`backend/src/bonds/bond-series-resolver.ts`) is the one function every write path calls inside its own transaction before it writes: a BUY or REINVEST takes the series named or the program's only series on sale on the transaction date, ADD_SHARES and an unpaired TRANSFER_IN must name one (`SERIES_REQUIRED`, never inferred), a removal's series is optional but checked at write time (`BondWriteGuard`, `backend/src/bonds/bond-write-guard.ts`, refuses `REMOVAL_EXCEEDS_SERIES` and `OVER_REMOVAL` inside the write's transaction), a named series must belong to the program, and a security with no program never carries one. The paths are `InvestmentTransactionsService` (`create`, which bulk, the AI executor, MCP and the scheduled post reach, `update`, the linked-transfer update, `transferSecurity`, `createEmbeddedForSplit`), the QIF/OFX and Money imports, the undo and redo of an investment transaction, and the AI and MCP previews (`bondSeriesCode`, a code such as `EDO1036`, resolved within the program; the resolved id rides in the signed descriptor). A form resends every field, so on update only a series that differs from the stored one is a request, and an edit that changes neither it nor the security, action or date keeps the stored value, NULL included. The imports store NULL for an acquisition they cannot resolve (`resolveImportedSeries`) and the undo restores the snapshot's series exactly (`restoredSeries`). A BUY or REINVEST without a stored series (written before the link, or imported) is read by `loadBondLedger` as a write would resolve it, and its lots are unknown (`SERIES_NOT_DETERMINED`) when that is not determined; an ADD_SHARES or unpaired TRANSFER_IN without one is never inferred. The purchase form asks `GET /bonds/securities/:id/series-on-sale` and `/series-holdings`. A redemption asks `GET /bonds/securities/:id/redemption-split` (`BondHoldingsService.redemptionSplit`), which finds the lots the removal takes by folding the ledger with and without a synthetic REDEEM through `bondLotsFromTransactions` (the write guard's own first-in first-out, never a second one) and sums the engine's `redemptionSplit` over the portions; it reads stored terms only and writes nothing. A series stored later (fetch, offer, cron, backfill) recomputes the program's securities after the commit (`BondPriceService.recomputeLinkedSecuritiesOfSeries`). INV-BOND-007.

## A bond program is followed on request, not by default

The daily series cron and the backfill fetch only the programs at least one security has switched `bond_auto_fetch` on for (off by default); otherwise a series enters the catalog by a fetch from the purchase form, an administrator's entry, or by the Refresh of a linked security, which fetches its program's current offer and then up to `PROGRAM_BACKFILL_CHUNK` (8) missing series of its history, newest sale month first (`BondSeriesService.fetchProgramOffer`). The Refresh has no throttle of its own, so the service bounds it in rows every replica sees: it claims the `fetch_sync` lease `bond-program-refresh:<country>|<program>` for `PROGRAM_REFRESH_INTERVAL_MS` (90 s) and never hands it back (a Refresh inside the interval fetches nothing and still recomputes prices), and each history series takes the lease `bond-series-attempt:<country>|<code>` for `BACKFILL_ATTEMPT_INTERVAL_MS` (24 h), so a series the source refused is not asked for again that day on any replica. `GET /bonds/programs` lists the catalog's programs for the picker (with the adapter's `infoUrl` for each). `GET /bonds/programs/:programId/refresh-progress` reports a running refresh from the program's `fetch_sync.progress`, written under the lease token by `FetchSyncService.reportProgress` (`phase` offer, series or done, `done`, `total`, `seriesCode`, `finishedAt`; empty with `phase` null when the program was never refreshed), for the client to poll. Nothing country-specific acts without a person: an adapter ships product templates (`backend/src/bonds/adapters/pl/templates/`, no per-series value) and its programs, never a series; the boot seed stores programs only; the benchmark refresh (NBP, GUS) runs, at boot and on its cron, only for benchmarks a stored series reads, and once after a series is stored for a benchmark never fetched, so a deployment where nobody adds a Polish bond sends no request to the issuer, NBP or GUS (`docs/specs/bond-program-securities.md` section 2.6). `docs/specs/bond-program-securities.md` sections 2.5 and 4.

## No country's bonds act without a person (INV-BOND-008)

A deployment holds the bonds its people chose and nothing else: a person in Poland follows Polish bonds, a person in Canada Canadian ones, and neither pays for the other's traffic or data. So no bond data is fetched or stored by default, for any country, now or in an adapter added later.

What a country adapter may ship: its business-day calendar, its benchmark definitions, its product templates (structure only: schedule, accrual, principal and rate rule types, observation, capitalization, redemption policy shape, rounding) and its programs. What it must never ship or trigger by itself: a series (series code, first-period rate, margin or spread, fee amount, sale window, source), a stored terms version, a benchmark observation.

When data is fetched or stored, and only then:

- a person fetches a series (the purchase form, `POST /bonds/instruments/fetch`, the AI and MCP tool), refreshes a linked security (its program's current offer and a bounded piece of its history), or an administrator enters one by hand;
- the daily series cron and its backfill, for the programs a person switched `bond_auto_fetch` on for, and no other;
- the benchmark refresh, at boot and on its cron, for the benchmarks a stored series reads, and once after a series is stored for a benchmark never fetched.

The boot seed stores programs only, so the form can offer them; it makes no network call. Adding a country (`docs/backend/bond-adapters.md`): implement the adapter to this rule and add it to `INSTALLED_BOND_ADAPTERS`; `backend/src/bonds/no-automatic-bonds.guard.spec.ts` and `backend/test/integration/no-automatic-bonds.integration.spec.ts` iterate the installed adapters, so the new one is checked without editing them. They fail when the boot seed stores a series or calls a fetch, when a cron fetches with no stored series and no program switched on, when a template carries a per-series value, or when the adapter type regains a series catalog.

## A bond series is fetched from its issuer's own source, and a person supplies only its code

`BondSeriesService` (`backend/src/bonds/bond-series.service.ts`) gets a series the catalog lacks from the adapter's official source (`fetchSeries`, `docs/specs/bond-series-fetch.md`) or, for an administrator, from `manualSeries` on the adapter's template. The service names no country: the adapter owns the host, the document formats, the templates and the provider id (`seriesProviderId`, `obligacjeskarbowe` for Poland, in `TRACKED_PROVIDERS`). Every request goes through `SeriesHttp.gated` (`backend/src/bonds/series-http.ts`), the one place that calls `fetch` for a series: breaker first (`assertAvailable`, `recordSuccess` once the whole body has arrived), `redirect: "manual"` so a 3xx comes back as its status and the adapter refuses it, a 30 s `AbortSignal.timeout`, and a body read as a stream with a 5 MB cap that cancels the read past it. The NBP and GUS benchmark fetches use the same door (`BenchmarkRefreshService` passes `{ allowedHosts: series.hosts }`, the hosts the adapter declares on each `BenchmarkSeriesDefinition`: `static.nbp.pl` and `stat.gov.pl`): https on a declared host only, a redirect followed only when its target passes the same test and at most 3 hops (`FetchRefusedError` otherwise, not counted against the breaker), with the same timeout and 5 MB cap. `provider-call.guard.spec.ts` names that file. A request carries a country and a series code and nothing else (`FetchBondSeriesDto`); a stored series answers `created: false` without a fetch; the write is `BondCatalogService.storeEntry` under `LockScope.BondSeriesFetch`, so a differing repeat is `SERIES_TERMS_CONFLICT` and nothing is written. The daily `bond-series.service` cron stores the series the issuer lists as on sale, for the programs a person switched `bond_auto_fetch` on for only. INV-BOND-006.

## A payload coarser than daily is a different series, not a sparse one

A provider asked for a long range may answer weekly or monthly bars; written into a daily table they overwrite the real daily rows on those dates, and under the one-basis-per-series rule monthly rows carrying adjusted closes made `loadPriceSeries` *drop every daily row around them*. `assertDailySeries` (`providers/daily-spacing.util.ts`) is the one test, and it runs inside `bulkUpsertPrices` -- not in its four callers, because a guard one caller forgets is not a guard (each caller already reports a failed security, so the throw surfaces as "this one did not update"). The threshold, the median (never the mean -- one long exchange closure must not make a daily series look weekly) and the minimum sample size live there too; `daily-spacing.util.spec.ts` fails on a second copy of any of them under `securities/`.

## History depth is a request, not a property of the holding

`backfillSecurityHoldingPeriod` clips its write to the first transaction date -- right for position valuation, wrong for backtests, the GEM report and performance comparison, which need prices from before the user bought. Both backfill endpoints take `range` (`BackfillPricesQueryDto`); supplying it means fetch that range **and** store all of it, omitting it keeps the clipped default. When adding a caller, decide which question it asks -- "what is this position worth over the time I held it" or "what did this instrument do" -- rather than reaching for `max`; the clip exists so an untouched catalogue does not accumulate decades of prices nobody reads.

## Exchange rates come from an ordered chain of providers

`ExchangeRateService` never names a provider. Every provider question it asks -- the daily refresh's latest rates, a backfill's or a gap fill's daily window, the live rate behind the portfolio summary -- goes through `FxProviderChain` (`src/currencies/providers/fx-provider-chain.ts`), built once by `CurrenciesModule` from `FX_PROVIDERS` (default `frankfurter,yahoo`; an unknown name refuses the boot with `FxProviderConfigError`). A provider is one adapter implementing `FxRateProvider` (`src/currencies/providers/fx-provider.interface.ts`): `carries(code)` gates every call, `fetchLatest(base, quotes)` answers one base against many quotes, `fetchDailySeries` a window, `fetchLive` an intraday quote where the provider has one. The design is `docs/specs/exchange-rate-providers.md`; INV-FX-005 is the invariant. Four things are load-bearing:

- **The provider dates and orients the observation; the service stores it.** An `FxObservation` carries its own `from`, `to`, `date` and `rate`, in whichever orientation the provider answered. `saveRate` and `persistRateSeries` orient every point through `canonicalRateRow` (INV-FX-003) and write the row on the observation's date -- a reference rate published for Friday is Friday's row whichever day the refresh runs -- under the `source` the chain attached, which is the answering adapter's own slug. No source literal exists outside `src/currencies/providers/`: `providers/fx-provider-source.guard.spec.ts` fails one, and fails an import of `yahoo-finance.service` under `src/currencies/` outside the Yahoo adapter, so a provider question cannot bypass the chain.
- **The refresh asks once per base.** `refreshAllRatesGlobally` sorts the currencies in use, groups the canonical pairs by their first code and calls `latest(base, quotes)` per base in sequence; a provider that publishes a whole base at once answers each group in one call, and one that quotes pair by pair fans out inside its adapter (`FX_FETCH_CONCURRENCY` in `yahoo-fx.provider.ts`). The summary keeps three failures apart, because they have three repairs: `No provider answered` (every carrying provider returned `null`; the next tick retries), `No rate data available` (answered, no rate; a reader resolves the last admissible day or sees the pair missing) and `No configured provider carries X/Y` (a fact about `FX_PROVIDERS` for the operator). The per-pair detail stays in the server log; the endpoint returns counts.
- **"Answered with nothing" and "did not answer" stay apart per provider.** The chain's `dailySeries` is `answered: false` the moment a carrying provider returned `null` and nothing was found, because that provider may hold history the others do not; `fillRateWindow` passes the flag through unchanged, and only an answered window is remembered as empty (`ensureRatesForDate`, `ExchangeRateHistoryService`). The backfill reports the two as `A provider did not answer` and `No historical data available`. The truth table is section 5 of the plan, and every row of it is a case in `fx-provider-chain.spec.ts`.
- **A provider's quirks live in its adapter.** Yahoo's below-1 inverse check and its direct-then-reverse window merge are `YahooFxProvider`'s, so a caller on the chain keeps them without knowing the provider; the sections below describe them where they now live.

## A cryptocurrency's rates come from the crypto provider, which claims every coin pair

A `CRYPTO` currency (`currencies.kind`) is priced by `CryptoFxProvider` (`src/currencies/providers/crypto-fx.provider.ts`, source `yahoo_crypto`) from Yahoo's `<COIN>-<FIAT>` symbol, the one a crypto security uses: the coin leg comes from the currency's `quote_symbol` (`quoteSymbolCoinTicker`, `src/currencies/currency-kind.util.ts`), the fiat leg is whichever fiat the pair names. The `CurrenciesModule` factory appends it after whatever `FX_PROVIDERS` names; its name is a `PairProviderName`, so `resolveFxProviders` refuses it as a token while `describe()` still lists it. **The chain asks it, and only it, about a pair with a coin on either side, and never about a fiat pair:** `FxRateProvider.claims` is consulted before `carries` on `latest`, `dailySeries` and `live`, because Yahoo's fiat adapter carries every code and would otherwise get a coin pair first, and the coin adapter carries every fiat code (as a coin's counterpart) and would otherwise answer a fiat pair as "nothing there" and hide an outage (INV-CRYPTO-002, INV-FX-005). It reads `currencies` through `withScopedDb`, cached for `CRYPTO_CURRENCY_CACHE_MS` and forgotten by `CurrenciesService` on a currency write, and reaches Yahoo only through `YahooFxProvider`'s pair-symbol methods, so the throttle and breaker apply. `ExchangeRateService.refreshCryptoRates` refreshes only the pairs with a coin side, run by the weekend tick `scheduledCryptoRateRefresh` (`docs/cron-jobs.md`); a coin without a price symbol is claimed but not carried, and the refresh says to map one on the Currencies page. `docs/specs/crypto-accounts.md` is the design.

## FX history is filled over the span the currency is used, in windows the provider still answers daily

The stored history of a currency pair usually begins on the day the daily refresh first ran: `ExchangeRateService.backfillHistoricalRates` skips any pair that already holds a row, and the cron writes today. Every report dated before that then reports a missing rate, correctly and permanently, and nothing on any screen let a non-admin do something about it.

`ExchangeRateHistoryService` (`src/currencies/exchange-rate-history.service.ts`) is that door. `GET /currencies/exchange-rates/coverage?code=EUR` answers what is stored -- `earliestDate`, `latestDate` and the number of calendar days covered, counting **either stored direction as the one pair it is**, because a row under `PLN->EUR` is evidence about `EUR->PLN` on that date too. It counts calendar days rather than rows, which also keeps the figure honest for pairs whose older rows predate the one-orientation rule (INV-FX-003). `GET /currencies/exchange-rates/stored?code=EUR` lists those rows, newest date first. `POST /currencies/exchange-rates/fill-gaps` fetches what is missing. `docs/specs/fx-history-gap-fill.md` is the contract; six things about it are load-bearing:

- **A missing row is not a gap, and a resolvable date is not a covered one.** Two bounds, deliberately different. `FX_MAX_RATE_AGE_DAYS` (45) decides what a reader is *told*: a date is unresolvable only when nothing falls in the 45 days before it. `MAX_OBSERVATION_GAP_DAYS` (10) decides what is *fetched*: a gap is a maximal run of dates with no observation within ten days. Ten clears every ordinary market closure (a weekend is three, Christmas Eve to the 2nd of January nine) and does not clear a month -- which is the point, because a history holding one observation per month is resolvable on every date and wrong on 29 days in 30. Planning on the 45-day bound reports such a pair as complete and fetches nothing, which is exactly what a history assembled by earlier decade-wide requests looks like. `rate-gap-plan.ts` is that policy as a pure function, for the reason `net-worth/series-rate-fill.ts` is one. A day-spine `LEFT JOIN` would report every Saturday as missing.
- **The span comes from the user's own data**, not from what is stored: the first date an account, security or posting of theirs uses the currency, through today. Deliberately wider than `backfillHistoricalRates`' discovery, which filters to open accounts, active securities and non-empty holdings because it is priming rates for current positions -- a history fill must cover the years a since-closed account was open, because "net worth over time" still reports them. A currency nothing of theirs uses fetches nothing at all.
- **No window may exceed a year.** Asked for decades in one breath the provider answers with monthly bars stamped on the 1st, and `persistRateSeries` would store them as daily observations under the wrong dates. `MarketIndexService` chunks at `FETCH_CHUNK_DAYS` for the same reason, but prices also have `assertDailySeries` inside `bulkUpsertPrices` behind them -- **exchange rates have no equivalent spacing guard**, so `GAP_WINDOW_MAX_DAYS` is the whole protection. Adding one is worth doing and has not been done.
- **A fetched window overwrites what it covers.** `persistRateSeries` upserts `DO UPDATE SET rate = EXCLUDED.rate`, including over a rate imported from Money, which is why the fill targets gap windows rather than re-fetching the span. Gaps close enough to share one window are packed into one anyway: a call covering a year costs what a call covering a fortnight costs, and a month-end-only decade has a hole every month -- one window each makes it 120 requests at eight a press, which no reader will sit through. `GAP_WINDOW_MAX_DAYS` bounds what packing can sweep up, so two holes more than a year apart are never joined.
- **One press is bounded, and says what it left.** `MAX_GAP_WINDOWS` windows or `GAP_FILL_BUDGET_MS` of wall clock, whichever comes first, with the rest reported as `windowsRemaining`; the plan is recomputed from what is stored, so pressing again continues where the last press stopped. Windows go oldest first -- a report fails from its start date -- and **sequentially**, because a burst from inside one HTTP request is what rate-limits everybody and because only one concurrent call can hold the breaker's half-open probe.
- **The cap is applied after the known-empty windows are dropped, never by the planner.** A window the provider has already answered with nothing cannot be filled by asking again, so counting it against the budget lets a pair whose history starts long after the reader's data does spend every press re-skipping the same dead years: `USDCAD=X` carries nothing before December 2003, so a ledger opening in 1996 planned seven dead windows, and once they were remembered they filled the whole cap and the fill fetched nothing at all. `planRateGapWindows` plans the entire span and `ExchangeRateHistoryService` budgets what is left after the memory has had its say.
- **What a provider carries for a pair is written down, in `exchange_rate_coverage`.** One row per pair in the canonical orientation (`from_currency < to_currency`, held by a CHECK): `earliest_available_date` is where the provider's history starts, `first_gap_date` is where the next fill resumes, and `probed_from` is the earliest date any fill has planned over. The span opens at the later of the first two instead of at the reader's first transaction. The third is what makes the second safe -- a reader who imports older transactions moves their first use behind everything probed, so the pointer stands down for one press rather than hiding those years for good. The database enforces the directions, not the caller: `GREATEST` for the two that move forward, `LEAST` for the one that moves back, both ignoring nulls. Process memory alone was not enough -- per replica, thirty minutes -- so every restart paid a provider call per dead year to re-learn the same fact; and two columns on `currencies` were not enough either, because a floor belongs to a pair and one currency has many. The row is scoped to the provider chain that wrote it (`providers`, the ordered source slugs): under any other `FX_PROVIDERS` it reads as all-`null` and the next write replaces the three dates instead of merging them, or a floor one provider set learned would hide history the next one carries. `docs/specs/fx-history-gap-fill.md` section 4.
- **A provider that answered with nothing and a provider that did not answer are two different outcomes.** The first is a 200 whose `providerHasNothingBefore` names where the provider's history starts -- the day after the *last* window of the leading empty run, not the first, so seven dead years name 2003 rather than 1997 -- remembered in an `EmptyWindowMemory` within the request and in `exchange_rate_coverage` across restarts, so the next press does not re-ask; the second is a `ServiceUnavailableException` and the client says to try later. This is `fillRateWindow`'s `{ stored, answered }` reaching a user-facing surface, for the reason the breaker section below gives: only the code that made the call knows which happened. Yahoo's own floor needs no special case -- a 400 whose body reads `Data doesn't exist for startDate` is already read as an answer about the symbol (`ABSENT_WINDOW_DESCRIPTION`).

The pair is still the request's code against the caller's own reporting currency, resolved on the server (`resolveUserDefaultCurrency`); a request cannot name a pair, and the same-currency case is a 400 rather than a fetch, because 1 is not a stored rate. The provider call is still `ExchangeRateService.fillRateWindow`, made public rather than copied, so one place asks the provider chain for a rate window and persists what it answers in the pair's one stored orientation (`canonicalRateRow`), under the answering provider's `source`. The Yahoo adapter (`src/currencies/providers/yahoo-fx.provider.ts`) is where the reverse symbol is tried whenever the direct one comes back empty or sparse (`isSparseRateSeries`, the `MAX_OBSERVATION_GAP_DAYS` bound the gap planner uses) and the denser answer is kept whole plus the other's bars only for days the denser lacks: Yahoo carries some pairs daily under one symbol and sporadically under the other (`VNDSGD=X` returned one bar a month where `SGDVND=X` had every weekday), so stopping at the first non-empty answer stored a month-end-only history. Correctness when two fills race is the existing `ON CONFLICT (from_currency, to_currency, rate_date)` upsert (mechanism 4 of `docs/concurrency-and-idempotency.md`); the in-flight promise map beside it is a coalescer for a double-clicked button and is documented as gating nothing.

Neither route is admin-only, unlike the deployment-wide backfill: the write is bounded to one pair and a handful of windows, and `exchange_rates` is shared reference data with no owner column, so the user id goes in the log line rather than in the row. The client half is `frontend/src/components/currencies/RateHistoryCoverage.tsx`, a section of the currency dialog rendered outside its `<form>` so filling history cannot mark the form dirty; it lists the stored rates in the dedicated rate history dialog and shows the summary alone inside the currency form, where a scrolling table would bury the save button.

**The listing groups by date; it does not pick a newest row.** `getStoredRates` reads both orientations, groups on `rate_date` and takes the canonical row out of each group with `ARRAY_AGG(... ORDER BY (from_currency < to_currency) DESC, id DESC)`, which is also the row the pending contract migration keeps where a pre-collapse date is held twice and the two disagree. The obvious `DISTINCT ON (rate_date) ... ORDER BY rate_date DESC` is what `fx-rate.one-door.spec.ts` reads as a newest-rate read outside the resolver, and it would fail the build; so would a doc comment putting those words near that ordering. A reverse-orientation row is listed as `roundFxRate(1 / rate)` with `inverted: true`, at the rate column's ten decimals and never money's four.

## An outbound provider is called through a breaker, and a failed call is logged once, with its cause

`fetch` rejects with `TypeError: fetch failed` for DNS, TLS, a refused connection, a proxy hangup and an `AbortSignal.timeout` alike, and puts the discriminating detail in `error.cause`. Logging `error.message` -- or worse `error.stack`, whose frames are all undici's -- produced issue #1265: thousands of identical lines, no cause in any of them, an unusable UI, and a container restarting into the same storm because the start-up market-index warm-up ignored its own cooldown.

So: **`describeFetchFailure`** (`common/http/fetch-failure.util.ts`) turns a caught error into one bounded line naming the cause chain and the socket fields; **`ProviderHealthService`** (`provider-health/`) owns the per-provider circuit breaker, the rate-limited failure log (`logFailure` -- silent for a call the breaker refused, and it reports what it suppressed), and the durable `provider_health` row the alert cron reads. Call `assertAvailable` (throws) or `tryRequest` (returns `"refused"`) **before** any queue or semaphore, `recordSuccess` on any response (a 404 proves the host answered), `recordFailure` on a rejection, and `logFailure` in the catch -- which counts as well as prints, because a request can fail *after* its headers arrived (a stalled body) and those never reach the fetch helper's own catch. One throw counts once however many doors see it. Both gates report which kind of admission they granted, and only a `"probe"` holder owns the exclusive half-open slot -- a straggler that releases one it never held frees somebody else's probe. A probe holder owes an outcome -- `recordSuccess`, `recordFailure`, or `releaseProbe` when the attempt never reached the provider's own host (the Yahoo crumb handshake gives up at the cookie step, whose hosts are not the API host: counting *that* as an answer kept the failure run oscillating and the breaker never opened). A probe that reports nothing holds the slot for two minutes, during which every call to that provider is refused with the provider healthy. `wouldRefuse` is the read-only predicate for deciding whether to *skip work*, never a gate. Where a `null` is cached as "no such thing", have the code that *made the call* report whether anyone answered (`fillPriceWindow`/`fillRateWindow` return `{ stored, answered }`) rather than interrogating the breakers afterwards -- it knows which providers it reached, where a breaker check is either too narrow (one provider, while the fill falls back to another) or too broad (any provider down anywhere disables the cache for everyone). Where the caller genuinely cannot report it, check that the provider actually answered -- a null from a refusal *or from a transport failure below the threshold* means "we did not get an answer", and caching it turns a two-minute outage into a day of poisoned lookups. And nothing here restricts Nest's log levels, so suppressing a line means not printing it at all: a `debug` line per refused call is the same flood one level quieter. Never log a provider failure from a `catch` yourself, and never pass `error.stack` as the diagnostic: `provider-health/provider-call.guard.spec.ts` fails on either, and on a new client under `src/securities/`, `src/payees/lookup/google-places/`, `src/bank-sync/providers/enable-banking/` or `src/currencies/` that reaches `fetch` without the breaker. The email side -- one alert per outage episode, a 15-minute minimum and a 6-hour floor, all three claimed in SQL -- is `docs/specs/provider-outage-alerts.md`.

Two asymmetries are load-bearing. The breaker lives in **process memory** because it describes what this replica's own sockets did; only the episode start and the notification markers are shared, because only those must outlive a restart. And a **start-up** warm-up honours per-item fetch cooldowns while a **cron** ignores them: a schedule is the operator's request, a restart loop is not.

**A page a user names is backed off per address, not put behind the breaker.** The `html_table` provider (`securities/html-table-finance.service.ts`) reads whatever address a security's `quote_url` holds, so its hosts are an unbounded set chosen by users. `ProviderHealthService` fits none of that: its id is a fixed `TRACKED_PROVIDERS` key, its row is persisted and alerts the administrators, and keying it by a user's hostname let one user trip another user's working site with a few previews of a closed port on the same host, and turned every dead page into an outage email. So the provider remembers a transport failure itself, per page address (the hop that failed, not the address the security names), in process, bounded, for ten minutes (`failedPages`), set and read by refreshes only: a preview neither waits out nor starts one, and keying by site let one slow page on a shared site stop every other user's page there for the rest of the run. A status the site chose (404, 403) or a refused address is never remembered, and nothing is persisted. A name or literal refused on its face is refused by the shared `isRefusedHostName` (`ai/validators/safe-url.validator.ts`); what a name resolves to is judged once, where the socket opens (`publicOnlyLookup`), so a slow resolver reads as an unreachable page and a private answer as a private address (`AiEgressRefusedError` in the cause chain), never the other way round. The redirect walk is `followRedirects` (`bonds/series-http.ts`), the loop the bond fetch uses. The page is read with htmlparser2's `Tokenizer` and a table builder of constant work per token (`html-table-reader.ts`), never `parseDocument` or `Parser`, whose open-element stack makes a hostile page cost the square of its nesting. The charset is the header's, else a byte-order mark, else a `<meta charset>` in the first kilobyte. Parsed pages are cached for five minutes, expired entries dropped on insert and the whole cache held to a row budget (`PAGE_CACHE_MAX_ROWS`). Concurrent loads of one address share a single download and parse (`pending`, dropped when the load settles, a rejection never kept), and a transport failure reaches the preview as `QuoteTableError("unreachable")` carrying the cause, so anything else the preview catches is a defect and is logged as one. A page whose numbers or dates can be read two ways is refused (`AmbiguousQuoteTableError`), never guessed. It answers the month-by-month gap fill with `fetchHistoricalWindowSeries`, so a month before the page's few weeks is `[]`, which the fill may remember as empty. The preview endpoint is `@DemoRestricted()`.

**Which statuses are an answer about a symbol, and which are a refusal, is a status question everywhere except 400, where it is a body question.** `YahooFinanceService` reads 404 and 422 as "there is no such series" and everything else -- 429, 5xx, 401 -- as the provider declining to answer, because only the first kind may be remembered as an empty window. A 400 is both at once: Yahoo refuses a window it has no history for with `chart.error.description` of `Data doesn't exist for startDate = ...`, which is a statement about this symbol over this window, and it refuses a request this client built wrong with the same status and a different description. `ABSENT_WINDOW_DESCRIPTION` is the one that decides; the body is read with `text()` rather than `readBody`, because `throttledFetch` has already recorded the non-OK response with the breaker. Reading the pair as one refusal is issue #1409: `USDCAD=X` carries nothing before December 2003, so `fillRateWindow` reported `answered: false` for every month of 2000-2003, `EmptyWindowMemory` could never be written for them, and each portfolio summary re-issued the same 76 doomed calls -- a loop with no convergence rather than a slow first load.

## A latest FX quote below 1 is checked against its inverse symbol

Yahoo's chart endpoint rounds `meta.regularMarketPrice` to the instrument's `priceHint`, four decimals for every currency pair, while the daily closes in the same response keep full precision. The response is a 200 either way, so a pair whose rate is small came back as a valid-looking figure with most of its digits gone and the daily refresh stored it: `IDRSGD=X` quotes `0.0001` against a close of `0.00007156`, `VNDSGD=X` quotes `0.0`, `JPYUSD=X` quotes `0.0063` against `0.006336` (issue #1604). The inverse symbol keeps those digits (`SGDIDR=X` quotes `13973.23`).

So the Yahoo adapter (`YahooFxProvider`, `src/currencies/providers/yahoo-fx.provider.ts`) checks every latest quote it answers -- the refresh's `fetchLatest` and the live rate's `fetchLive` alike -- and the choice is the pure `chooseFxQuote` in `src/currencies/quoted-rate.util.ts`. A quote of 1 or more is taken as it stands; a quote below 1, zero or absent sends the same question to the inverse symbol, and of the two the larger rate (more significant digits at the same four decimals) is the observation, stored through `canonicalRateRow` like any other. When the best quote either way is below `MIN_PRECISE_QUOTED_RATE` (0.1, where the rounding is still at most 0.05% of the rate) nothing is stored: the refresh reports the pair failed and names it in the log, and a reader resolves the last admissible day or reports the rate missing (INV-FX-001). A pair whose direct quote is 1 or more costs one call and any other costs two, every time: nothing remembers which symbol answered, because that would be per-replica state. The historical and intraday paths read the full-precision closes and are not affected.

## A read may fetch the exchange rates it is short of, through one door, and re-read them

`ExchangeRateService.ensureRatesForDate(pairs, date)` is the only way a read path asks the provider for rate history it does not have. The daily refresh writes today only and `backfillHistoricalRates` skips a pair the moment it holds any row, so a report or a chart over a span nobody ever loaded names every figure incomplete for rates the provider has had all along -- this fetch is what closes that. Its unit is the calendar month around `date` (plus the boundary lead), persisted in the pair's one stored orientation, with an empty month remembered for thirty minutes; it is best-effort, never throwing for a provider failure, and returns the number of observations stored.

Its callers are `accounts/account-balances-report.service.ts` (`ratesForReport`, for a point-in-time report -- `docs/specs/account-balances-as-of.md` section 7.1) and `net-worth/series-rate-fill.ts`, the shared planner for a *series*: `NetWorthService.getDailyInvestments` / `getInvestmentBreakdown` / `getMonthlyNetWorth` / `getMonthlyInvestments`, and `PortfolioPeriodResultService`. The series form turns the per-point `missingRatePairs` into `(month, directionless pair)` units, capped at `MAX_FILL_MONTHS`, and is opted out of with `fetchMissing: false` by anything that must not reach the network -- `getLlmHistory`, the AI assistant's and MCP's door, passes it, and so does `PortfolioService.getPortfolioSummary` for its since-inception result. That last one is not about the network being forbidden but about who is waiting: the window opens at the scope's first investment transaction, so a summary card drove a backfill over every month a twenty-six-year history had no stored rate for, inline, on a request a person was watching a spinner for (issue #1409). The summary already withholds a figure with its cause, so it reports the gap; filling it belongs to `ExchangeRateHistoryService` and the scheduled jobs. Every caller obeys the same two rules: what was fetched is **re-read from the database** rather than patched into the index it already holds, and a pair the provider does not carry stays missing with the figure withheld (INV-FX-001, `docs/time-series-contract.md` section 2.2).

## A day's market movement is a value difference minus the reader's own contributions, and it is decided once

`GET /portfolio/daily-movements` (`securities/daily-movement.service.ts`) reports `MV(d) - MV(d-1) - externalFlow(d)` per calendar day. Price-only is the plausible mistake and it is wrong twice over: a 1,000 deposit reads as a gain and a paid dividend reads as a loss, because in both cases the value moved for a reason the market did not supply. The measure, and the invariants behind it, were already decided for the daily notification (`docs/specs/portfolio-movement-notifications.md`); this endpoint reuses them rather than inventing a second answer to the same question.

What is shared, and why each one is a single writer:

- **Which rows are external flow** is `loadExternalFlowSubtotals` (`securities/external-flow.util.ts`), extracted from `PortfolioMovementAlertService`. Both callers pass their own scope and window; neither spells the predicate out. It uses `investmentLinkedTransactionExclusion` / `investmentLinkedSplitExclusion` rather than an action list (INV-REPORT-001, INV-PORTMOVE-006), and excludes a transfer whose counterparty is also in scope, because cash moved between two scoped accounts never crossed the boundary. `external-flow.util.spec.ts` pins the original statement verbatim: that literal is what proves the extraction changed no row. Both callers read it with `perDay: true` and convert each `(date, currency)` subtotal at **that date's** rate; a whole window folded at the run day's rate reports the FX move between the two dates as a market return (INV-PORTMOVE-007).
- **When today's valuation was actually struck** is `PortfolioService.getLatestPriceObservations`, the dated form of the `DISTINCT ON (security_id)` read that `getLatestPrices` already ran (which is now derived from it, so the two cannot name different rows). A consumer asking "is this figure evidence about the period I am measuring, or a close carried forward from before it" reads that date rather than issuing a second query, which would be a second merge rule. The daily movement notification records each held close and its date with its baseline and restates the baseline when a late close arrives (INV-PORTMOVE-008, `notification-center/portfolio-price-freshness.util.ts`); valuation itself keeps carrying a close forward, which is correct.
- **Which accounts are in scope** is `resolveInvestmentScopeAccountIds` (`securities/investment-scope.util.ts`). A brokerage and its cash sleeve are one portfolio wearing two rows, so a filter naming either means both. `NetWorthService` held three copies of that widening; they now read the one helper.
- **What priced a position on a day** is `positionClosePointAsOf` (`net-worth/position-price.util.ts`), the same merge of the accepted store and the legacy transaction series that valuation uses, now also returning the date the close was struck on. That date is the whole trading-day question: a carried close moved nothing, so a day on which no HELD security struck a close is **blank** -- a third state, not an unknown, and the one the reader has nothing to fix about.
- **Whether the figure may be reported at all** is `decideDailyMovement` (`securities/daily-movement.util.ts`), a pure function table-tested against the design's truth table B. A change needs two complete values of two different observations plus a convertible flow; the client reads `complete` and `reasons` and re-derives no row of that table.

Two subtleties the shapes encode. A **zero baseline** yields no percentage but a known movement, so `movement` survives with `complete: false` -- the cell stays blank, the day panel may show the figure. And the detail endpoint's **`remainder`** (the move no per-security close explains: a dividend, a position first priced that day, cash interest) is `null` whenever any component is unknown, because a remainder computed from a subtotal is a reconciliation that reconciles nothing.

## An intraday bar is valued at its own day's positions

The 1D / 1W / MTD / 1M series (`PortfolioService.loadIntradayData`) takes its prices from the quote provider's bars and everything else from the daily investment fold: `NetWorthService.getDailyInvestmentPositions` returns, per calendar day, the share counts, closes and cash the fold valued that day at, and each bar reads the entry for its own UTC day. Never value a past bar with the `holdings` row or an account's current balance -- both are today's, and a trade or deposit last week then moves every bar before it. Each finished session also gets one closing point, one grid step after its last bar, carrying the daily series' own `value` for the day, so the intraday chart and the 3M chart agree on every close to the cent. The window is `presetWindowStart` and the series opens on the closing point of `presetEarliestDate`'s day (`planOpeningClose`), the same arithmetic and the same `getLastPricedDays` session the period-result service reports under the chart, so the first point and the caption name one session; never compute a lookback of your own. `docs/specs/intraday-historical-positions.md`, INV-INTRADAY-001.

## The portfolio summary is computed once per user, scope and minute, and forgotten where it stops being true

`PortfolioService.getPortfolioSummary` is the most expensive read in the application: live FX priming, a per-holding cost-basis replay, and a day-by-day since-inception result. Opening the Investments page issued three requests that each needed it -- `GET /portfolio/summary`, `GET /portfolio/allocation/by-tag` and `GET /portfolio/tag-keys` -- and they start together, so the server computed the same valuation three times concurrently.

`backend/src/securities/portfolio-summary-memo.ts` holds it. The key is `userId | sorted accountIds (or "all") | reporting currency | ambient identity`. Every input that changes the answer is part of the key rather than a reason to bypass the memo: a display currency that is not the preference is a different key, not a fresh computation; the ambient identity is in the key because a delegate reads the owner's accounts under the delegate's RLS identity, and the answer it computes is not necessarily the answer the owner's own request would compute. The reporting currency is therefore resolved before the memo, from the same `preferredCurrency(pref)` read the computation used to do first.

The entry holds the **in-flight promise**, not only the settled value: that is what makes three simultaneous requests await one computation rather than start three. A rejection is never remembered -- the entry is dropped so the next caller recomputes instead of inheriting a failure for a minute. Entries expire 60 s after the computation **settles** (`PORTFOLIO_SUMMARY_MEMO_TTL_MS`, the same window the intraday price cache in the same service uses) and the map is bounded at 256 entries, evicting the oldest first. The TTL runs from the answer, not from the start of the work: stamped at the start, a 48 s valuation was servable for 12 s and the next page open paid for the whole walk again (issue #1409). An in-flight entry has no expiry at all, so every caller that arrives during a long computation shares it; an invalidation that lands while it runs drops it, and the settling value does not put it back.

It is wrapped at the service boundary, so the controller, `loadTaggedAllocationInputs`, the security detail page, Monte Carlo and the AI / MCP `get_portfolio_summary` tool all share one answer without knowing the memo exists.

The day-by-day investment valuation underneath it is shared too, but only while it runs. `backend/src/net-worth/daily-investments-in-flight.ts` lets identical concurrent calls of `NetWorthService.getDailyInvestments`, `getSampledInvestments` and `getDailyInvestmentPositions` await one walk: the period results batch and the value chart on its All range ask for the same since-inception series together (issue #1888). The entry is dropped when the walk settles, so nothing is answered from a finished valuation. The key is the resolved window, scope, reporting currency, `collectPositions`, the `fetchMissing` opt-out, the ambient identity and the request timezone. A caller inside a transaction never shares. The seams below drop these entries with the memo's, so a read that starts after a committed write does not join a walk that began before it.

`invalidatePortfolioSummary(userId)` is called wherever a memoized valuation stops being true:

| Seam | Where |
|---|---|
| Any money-moving write, after it commits | `NetWorthService.triggerDebouncedRecalc` and `recalculateAccount` (INV-CACHE-001) -- immediately, not on the debounce timer |
| A provider quote or a historical bar | `SecurityPriceService.savePriceData` and `bulkUpsertPrices`, which between them carry refresh, refresh/selected, daily settlement and every backfill |
| A manual price create, update or delete | `SecurityPriceService.scheduleSnapshotRecalc`, which also covers a security no account holds |
| The transaction-price maintenance pass | `backfillTransactionPrices`, whole memo: there is no single owner |
| A backup restore, a demo reset, an undo or a redo | `BackupRestoreService.restoreData`, `DemoResetService.performDemoReset`, `ActionHistoryService.undo` / `redo` |

**The memo is process memory; its invalidation is not.** The entries are per replica, so N replicas cost N computations of the same summary -- that is the bargain, and it is the same one the intraday cache next door makes. What is *not* on offer is a stale answer after a write: an invalidation is announced on the `EVENT_BUS` (`PORTFOLIO_SUMMARY_INVALIDATION_CHANNEL`, wired by `PortfolioSummaryInvalidationBridge`) and every replica drops the user's entries. Without it, a write served by pod A left pod B answering from its own memo for up to 60 s, and a load balancer with no affinity sends the next read there: the Investments page showed the portfolio as it was before the trade the person had just entered. The `CLUSTER_MODE=multi` E2E shard caught that (issue #1409); `docs/system-invariants.md` INV-CACHE-001 carries the rule.

**The announcement is a hint, and the TTL is still the bound.** `NOTIFY` can be lost -- a replica whose `LISTEN` connection is reconnecting misses everything sent while it was away -- so a dropped message leaves that replica's entry alive until it expires, exactly as before the channel existed. The payload is a user id and nothing else: the recipient drops a cache and recomputes from the database under its own scope, which is the only response `common/events/event-bus.interface.ts` permits to a wake-up. The bridge takes the bus `@Optional()`: `EventBusModule` is `@Global()` rather than imported by each feature module, so a graph assembled without it -- the integration harness builds one from the feature modules alone -- keeps the local-only invalidation and says so in the log, instead of failing to compile. The announcement is made immediately after the local drop and is never awaited: a bus that is down must cost the request nothing. It therefore rides exactly the same seam, with exactly the same timing, as the drop it mirrors -- including the callers that invalidate from inside their own transaction, where both are made a moment before the commit is visible. That window is the seam's and predates this channel; what the channel changes is that the other replicas are now in it too, rather than outside it for a minute.

`getPortfolioTagSummary` is the one caller that was removed rather than memoized. Which tags the held securities carry is a question about `holdings`, `securities`, `security_tags` and `tags` -- no price, no rate, no cost basis -- so it is one scoped query under the valuation's own held predicate (`ABS(quantity) >= 0.0001`). It reports `keys` (the distinct KEY:VALUE namespaces) and `hasTaggedHoldings` separately, because a portfolio tagged only with plain labels has no keys and still has a by-tag grouping worth offering. It is also more honest than the path it replaces: the valuation-based one dropped an unpriced or unconvertible holding's slice from the allocation, so a late price feed silently removed a tag key from the switcher.

## The bonds on sale and the history of their terms are read from the catalog, never fetched on the request

`BondOfferService` (`backend/src/bonds/bond-offer.service.ts`, `docs/specs/bond-offer-and-history.md`) answers `GET /bonds/offer?countryCode=PL[&assume=...]` and `GET /bonds/history?countryCode=PL[&programCode=EDO]` from stored reference data only; the catalog is filled by a person's actions (the Refresh of a linked security, a fetch from the purchase form, an administrator's entry) and, for the programs switched to auto-fetch, by the daily series cron and its backfill (`docs/cron-jobs.md`, `backfillCodes` on the adapter). A series is on sale when the user's financial today (the day `BondPriceService` uses) lies in the `saleWindow` of its newest terms version. Its projection is the engine's own `valueBondLot` on one bond bought today, reached through `BondValuationService.loadReference` and `valueLotFrom` and the `ParseAssumePipe` map, so a preview and a valuation share code: `maturityValue` is the sum of every cash flow (a coupon bond's coupons and the face value, not reinvested), null when any amount is unknown, and `annualizedReturn` is `annualizedReturn` (`backend/src/bonds/domain/annualized-return.ts`), a bisection over `ExactDecimal` to 4 places. An assumption applies only to the series that read its benchmark. The history's `coverage` lists the sale months with no stored series between the earlier of the adapter's `seriesValidFrom` and the earliest stored month, and the latest stored month. The service names no country, so the country-agnostic guard covers it.

## A bond-linked security's close for a day

A series that values a held position by multiplying its quantity by a stored close reads the close through `valuationClosePointOn` (`backend/src/securities/bond-valuation-close.util.ts`). For a quoted security that is `positionClosePointAsOf`: the newest accepted close at or before the day, merged with the legacy transaction fallback. For a bond-linked security it is the engine's row of that day and nothing else. The engine writes a row for every calendar day it can value the lots and none for a day it refuses (a lot whose series is not determined, a started period without its benchmark, a refused purchase), deleting older rows there, so a missing day is a refusal: carrying the previous engine close over it prices lots the engine cannot value, and a transaction price is one lot's trade price, never the holding's value (INV-BOND-002, INV-BOND-005, INV-BOND-010). The reader reports the security unknown for that day through its completeness channel. Example: 100 bonds priced 111.62 on 2026-10-13 and an imported BUY of 10 at 100.00 with no series on 2026-10-14; from 2026-10-14 the engine refuses, and the blend that read 110 x 100.00 = 11,000.00 as a settled figure now reports the security unknown (A26-M26). `INV-BOND-010` lists the readers not yet moved to it.
